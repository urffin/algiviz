# Переиспользование диспетчера массива

[English](../array-dispatch-performance.md) · [Исходный порядок работ](performance-baseline-0.13.0.md#порядок-оптимизации)

Локальная реализация проверена 2026-11-13. `createArrayRenderer` создаёт один
scene dispatcher на экземпляр, поэтому повторные промежуточные кадры используют
кэш сопоставления одной пары. Функция рисования создаётся на каждый вызов и
передаётся как context диспетчера: она захватывает актуальные размеры, Canvas,
палитру, progress, event и состояние. Диспетчер её не сохраняет. Вложенный вызов
на другом Canvas не подменяет данные внешнего кадра; ошибки проходят через
существующий `finally` с восстановлением настроек Canvas.

## Основание сравнения

До — точная копия `src/canvas/index.ts` из `25040d157527e7564bde088b3c5b76bdcc398ecf`,
сохранённая в `test/fixtures/array-dispatch-before.ts`. Она транспилируется имеющимся
TypeScript без загрузки зависимостей и использует тот же текущий /scene, что и
новая версия. Это изолирует изменение /canvas от уже выполненной оптимизации /scene.
Fixture также позволяет выполнять регрессии в shallow checkout CI без старой истории Git.
JSON содержит SHA-256 исходников, сборки и измерительного кода; текущие исходники
и dist сверены с браузерным отчётом после окончательной сборки.

Сортировки вставками и пузырьком: 24 и 2 000 элементов, обратный порядок.
Существующий ограниченный профилировщик выбирает до 16 пар из префикса трассы,
по 8 промежуточных кадров на пару. Проверены повторная пара, воспроизведение,
смена пары на каждом вызове, точные ручные шаги и обратная перемотка.
Каждый случай измеряется в порядках до/после и после/до, с прогревом и 7 выборками.
Замеры выполнялись отдельно от тестов и сборки.

Windows x64, AMD FX-8350, Node 22.17.0; встроенный Chromium 157, DPR 1,
видимая страница, основной bitmap 960 × 540. Масштаб не менялся.
Перед браузерными замерами выполнялось чтение пикселей: оно может влиять на
Canvas backend. Флаги backend не задавались. Это время CPU/отправки команд,
не FPS и не ожидание завершения GPU. Node использует счётную Canvas-заглушку.

## Результаты

Мс на кадр, до → после. Диапазон — две медианы из противоположных порядков,
не доверительный интервал. В колонках Node показан второй независимый прогон;
первый также сохранён и учитывается в выводах о разбросе.

| Сценарий | Node, одна пара | Node, воспроизведение | Canvas, одна пара | Canvas, воспроизведение |
| --- | --- | --- | --- | --- |
| insertion-24 | 0.042–0.044 → 0.028–0.031 | 0.047–0.054 → 0.033–0.036 | 0.338–0.375 → 0.309–0.334 | 0.325–0.378 → 0.325–0.406 |
| bubble-24 | 0.044–0.055 → 0.027–0.029 | 0.047–0.047 → 0.033–0.035 | 0.363–0.477 → 0.352–0.369 | 0.400–0.414 → 0.338–0.344 |
| insertion-2000 | 1.924–1.970 → 0.833–0.893 | 2.306–2.327 → 1.260–1.295 | 2.288–2.650 → 1.550–1.613 | 5.694–6.116 → 5.194–5.641 |
| bubble-2000 | 1.993–2.073 → 0.911–1.067 | 2.484–2.602 → 1.279–1.301 | 2.000–2.113 → 1.388–1.463 | 5.863–6.213 → 5.200–5.266 |

На больших массивах браузерное воспроизведение дешевле примерно на 8–15% в
соответствующих парных замерах. Выигрыш на небольших сценах менее устойчив:
например, insertion-24 не улучшился. Кэш полезен при нескольких кадрах на пару.

Промахи не дают устойчивого ускорения и местами замедляются. У bubble-2000
смена пары во втором Node-прогоне: 4.081 → 4.314 и 3.748 → 4.405 мс;
в Canvas: 3.675 → 3.775 и 3.500 → 3.525 мс. В первом Node-прогоне
insertion-2000 менялся с 5.28–5.55 до 7.24–7.76 мс, а во втором — с
3.94–4.42 до 3.79–3.94 мс. Этот разброс не позволяет обещать отсутствие
регрессий на промахах. Ручные шаги и перемотка также имеют смешанные результаты.
Полные данные этих случаев сохранены вместе с интерполяцией.

## Корректность и память

Регрессии сравнивают последовательности команд со старой реализацией на всех
окнах четырёх сортировок и дополнительных случаях: смена размеров/Canvas,
изменение event на тех же снимках, held, highlight, sorted prefix/suffix,
нулевые и отрицательные значения, пустой массив, вход/выход объектов,
разные progress и перемотка. Проверены светлая, тёмная и своя палитры,
неизменность входных снимков, вложенный render, ошибка посреди рисования
и повторное использование после неё. В браузере все **696 сравнений пикселей**
прошли; настройки вызывающего Canvas восстановлены.

Два Node-прогона дополнительно пропустили по 4 000 пар из 512 элементов
через каждую реализацию. После каждых 1 000 пар выполнялась явная GC.
WeakRef старых снимков и последних context/event/frame обнулились; обе версии
удерживали два активных снимка через существующий projector, после удаления
renderer не осталось ни одного. Во втором прогоне куча процесса до/после:

| Реализация | После 1 000 / 2 000 / 3 000 / 4 000 пар, MiB |
| --- | --- |
| До | 35.056 / 35.064 / 35.066 / 35.087 |
| После | 35.130 / 35.146 / 35.165 / 35.166 |

Размеры включают весь процесс с TypeScript. Разница около 0.08 MiB на этой
форме данных не является точным размером кэша. Аудит владения и эти выборки
показывают ограниченное O(n) удержание, а не доказательство по всем трассам.

Окончательные `npm test` (193 теста), `npm run test:package` и
`npm run test:bundle` прошли. Публичный API, версия и зависимости не менялись.
Публикация и CI нового коммита здесь не выполнялись.

Следующий кандидат исходного плана — профиль категорий нативных команд Canvas
перед выбором кэширования декораций или группировки. Эта работа его не начинает.
