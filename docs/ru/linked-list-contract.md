# Будущий связный список: эскиз контракта и совместимость с ядром

Датированные разделы ниже описывают этапы проектирования и реализации.

## Вывод и объём

Вставка, удаление и перенаправление указателей укладываются в нынешние Step,
Frame, Scene, generic registry и Player. Для предложенного объёма не требуется
менять существующие публичные поля, unions событий, виды сцены или entry.
Блокер ядра перед 1.0 не найден. Будущий отдельный entry сам добавит публичный
API, потенциально как minor-возможность по U3 при совместимости прежних вызовов;
сейчас он не добавляется.

Первый объём — конечный **ациклический односвязный список**, включая пустой и
одноэлементный, с неизменяемыми полными снимками. Вставка/удаление в любой позиции,
перестановка/разворот и корректная смена указателей выражаются атомарными изменениями
снимков; trace-методы и алгоритмы пока не выбраны. Циклический/двусвязный список,
sentinels, несколько списков с общими узлами, аллокатор и общий отладчик указателей
вне объёма. Будущим вариантам нужна отдельная ревизия API/совместимости, а не
неявное расширение закрытых next-only type-map или union.

## Модель и инварианты

Концептуальные данные, не экспортированный TypeScript:

```text
headId: ID узла | null
nodes: { id, value: T, nextId: ID узла | null }[]
layout: ID узла -> конечные x/y либо неизменяемая политика раскладки
annotations: ID узлов/указателей -> постоянные role/data
result: выбранные ID/порядок узлов либо прикладные метаданные ответа
```

Порядок хранения nodes не является порядком списка: цепь определяется проходом
от headId по nextId. Хвост и длина вычисляются из неё; будущие кэшированные значения,
если появятся, обязаны ей соответствовать и не становятся независимым входом
топологии. Отдельная изменяемая таблица рёбер не дублирует nextId как второй
источник истины.

Каждый полный снимок модели удовлетворяет правилам:

- ID — уникальные непустые примитивные строки. Равные value/подписи не делают
  узлы одинаковыми. Позиция, индекс и номер в обходе не являются идентичностью.
- Пустой список имеет headId: null и пустой nodes. У непустого голова существует.
- Каждый ненулевой nextId ссылается на существующий узел. Null означает отсутствие
  следующего, а не неизвестный ID, фиктивный узел, undefined или неявный sentinel.
- Проход от головы посещает каждый узел ровно раз и заканчивается null. Циклы,
  петли, недостижимые узлы и общий successor с двумя входящими next недопустимы.
  В голову не входит next; хвост один.
- Ссылки отметок/результата на текущие сущности и нужные координаты корректны.
  Отметка/курсор удалённого узла атомарно снимается или переназначается;
  исторический ответ можно хранить отдельными скопированными прикладными данными.

Будущий модуль проверяет обновление целиком до фиксации/выдачи шага. Просто
переназначить A.next на C нельзя, если B остаётся членом модели, но недостижим:
удаляем/переносим B в том же обновлении либо используем отдельный рабочий вид.
Вставка X между A и B фиксирует X.next=B и A.next=X вместе; удаление B вместе
фиксирует обход предшественником и исключение B. Голова/хвост/последний узел
подчиняются тем же правилам. Точные входы, методы, выдача ID, классы и порядок
ошибок требуют следующего API-контракта. Общий Scene этих правил не проверяет;
будущий валидатор или алгоритм изменения списка здесь не реализуются.

## Учебные отдельные присваивания указателей

Корректные атомарные снимки не описывают всю локальную работу алгоритма.
После выделения X и X.next=B, но до A.next=X, X может быть отсоединён, а в B
могут входить две стрелки рабочего вида. При удалении выделенный отсоединённый
узел или локальный курсор могут оставаться видимыми после обхода. Такая рабочая
арена **не является корректным полным списком или деревом** по нашим эскизам.

Её можно хранить в отдельном прикладном State: например, корректный снимок списка
плюс локальные выделенные узлы/ссылки/контекст операции либо полностью прикладная
арена урока. Нынешние generic Step/Frame и собственные сцены показывают микрошаги
без новой фазы ListState/Player и без ослабления валидатора полного списка.
Нельзя передавать арену будущему list/tree validator как корректную цепь.
Публичному staging builder или неограниченному setNext нужен отдельный контракт;
эскиз не обещает их неявно.

Для показа dangling/freed-ссылки учебный вид сохраняет явные diagnostic/tombstone
данные либо осознанно рисует неразрешённую ссылку. scene.get не разыменует сущность,
отсутствующую в обеих endpoint-сценах. ID-ссылки — данные, не реальные машинные
указатели или команды владения памятью.

## Идентичности узлов и указателей

ID узла сохраняется при смене значения, позиции, статуса головы или следующего
узла. Новая логическая сущность получает новый ID даже при равном значении.
Не следует переиспользовать ID внутри сохранённой истории: seek может пропустить
разрыв и сопоставить разные сущности. Restart создаёт свежий источник/сеанс и
не меняет старые снимки.

Логический next принадлежит **слоту next владельца**. Его идентичность — условно
(ID владельца, 'next'), независимо от цели. Проекция может явно материализовать
ID указателя из этого слота, а не из пары owner-target. Поэтому A.next=B ->
A.next=X обновляет прежний указатель. Удаление владельца удаляет его указатель;
новому узлу принадлежит другой слот.

Условные виды сцены — listNode и listPointer; точные имена ещё не выбраны.
Данные узла могут содержать значение/позицию/отметки, указателя — scene ID
владельца и nullable scene ID цели. Полезная стратегия — объект указателя для
каждого узла, включая null next: переходы null-to-target и target-to-null остаются
update. Маркер null/короткий штрих рисуется pointer handler без фиктивного узла.
Станет ли это default штатной проекции — следующее решение rendering/API.

Если другая проекция пропускает null-слоты, они enter/exit при появлении/снятии
цели; scene.get найдёт только объявленные на одном из endpoints слоты. Registry
нужен заранее выбранный стабильный набор видов; head/tail/cursor-декорации могут
быть расширением приложения, а не новыми обязательными видами позже по U3.
Scene ID различают список/представление/вид/узел/слот, графы, деревья и другие
списки. Tuple-кодировка — пример, не публичное обещание интеграции.

## Кадры, перенаправление и рисование

При вставке старые узлы сохраняют идентичность, новый узел/слот появляются.
Указатель предшественника содержит прежнюю и новую цели. Раскладка может сдвигать
узлы, освобождая место, без смены ID. Удаление делает exit узла и принадлежащего
ему указателя; предшественник переключается на оставшегося successor либо null.
Старые данные удалённой цели доступны через scene.get даже при нулевом presence.
Это данные анимации, не разрешение на dangling-ссылку в зафиксированной модели.

Pointer handler должен читать **оба previous/current** указателя, разрешать
соответствующие переходы владельца/цели и выбирать позиции нужного endpoint.
Перед scene.get проверяется null. Чтение только current target может дать скачок
или потерять геометрию исчезающей связи. Ядро предоставляет данные, но не выбирает
morphing/crossfade стрелок, форму null-маркера, routing или opacity. Эти defaults
требуют отдельного дизайна и визуальной приёмки. Геометрия промежуточного кадра
не является третьим списком; возможны пересечения/наложения.

Проекция чистая по неизменяемому State/захваченной политике. Позиции находятся
в State или детерминированно вычисляются из цепи/порядка/view state. Смена
захваченной раскладки требует нового projector. Преобразование viewport/DPR при
рисовании одинаково для узлов/указателей; mutable viewport не является входом
endpoint-cache. Новых next/parent/relation-полей Frame/Scene нет.

Canvas перерисовывает кадр. SVG/DOM с сохранением элементов сверяет нарисованные
ID каждый кадр: seek может пропустить callbacks вставки/удаления. Pointer handler
может вызываться с нулевым presence. Порядок использует текущий zIndex; scene.get
не зависит от того, какой handler уже нарисовал объект. Гарантированного жизненного
цикла каждого узла из этого не следует.

## Связь с /graph и /tree

Полный снимок списка отображается в направленный граф: доменные ID узлов
сохраняются, ненулевой next становится ребром с явным ID слота, а не пары концов.
Null-слоты/head-маркеры остаются метаданными/декорациями. Список строже графа;
произвольные графовые данные не обходят проверку корректной цепи.

Эскиз /graph фиксирует топологию на trace. Вставка/удаление узлов или смена концов
не становятся допустимыми для такого trace только потому, что отдельный снимок
можно представить графом. Список использует generic playback/scene напрямую.
Общая будущая геометрия/внутренний код не требуют публичного наследования или
зависимости. Nullable pointer списка не становится автоматически входом graph
edge handler.

Полный ациклический список также является вырожденным упорядоченным деревом с
корнем head и максимум одним ребёнком у узла; пустой — пустым деревом. Null не
является ребёнком. ID next-слотов можно явно задать как tree link ID. Рабочая
арена с отсоединёнными узлами, общими целями или временными циклами таким деревом
не является. Правила дерева и первый объём графа сохраняются; конвертации и
адаптеры не реализуются.

Список, граф и дерево сосуществуют в составном generic registry с уникальными
scene ID. Общие данные не требуют расширять ArrayEvent, будущие graph/tree events,
статусы Player или требования существующих registry. Точные entry, адаптеры и
границы optional-rendering — отдельные решения API модуля. Модель остаётся
headless и DOM-free.

## Playback, владение и проверка

Прикладные `Step<ListState<T>, ListEvent>` и `Frame<ListState<T>, ListEvent>`
подходят createStepEmitter, createPlayer/createTimeline и Player stepSource/
isTerminal. Даже пустой список выдаёт начальное состояние/шаг; нынешнее требование
playback к непустому источнику сохраняется. State содержит цепь, указатели,
отметки и результат; renderer не восстанавливает их из истории событий.
Ролям нужно явно открытое расширение или
типизированный payload, не глобальный закрытый словарь всех алгоритмов.

Pause, Next, final hold, Restart и dispose сохраняют правила. Финальная работа —
до terminal yield, очистка — в finally. Previous читает сохранённые снимки, не
выполняет обратные присваивания; eviction использует позиции, не ID или step.index.
Restart восстанавливает исходную цепь без прежних отметок/результата. State-only
asyncSource/Worker по-прежнему завершаются по EOF с undefined event; постоянной
визуализации Frame.event не требуется.

Собственные узлы/метаданные/коллекции копируются и замораживаются, неизменившиеся
части можно разделять. Payload T — неизменяемые/cloneable данные приложения.
Нельзя менять или transfer-detach хранилище, удерживаемое playback/историей.
Worker shared-memory ограничения прежние. Dispose закрывает источник/сеанс,
а не освобождает узлы как в C и не обещает немедленную сборку мусора. Поиск,
раскладка и неизменяемый снимок имеют свою стоимость помимо O(1) смены указателя;
из неё не следует O(1) snapshot/draw. Бюджет Player не прерывает один дорогой
next/projection/render.

Изолированная проверка прошла **37/37 runtime-сценариев** и четыре strict-
конфигурации TypeScript 6.0.3: NodeNext/Bundler × headless ES2022/Player DOM,
с десятью отрицательными list type-cases. Рукописные прикладные состояния/сцены
проверяют вставку, удаление, null-переходы, разворот, доступ к старым/новым целям,
рабочие микрошаги, rewind/seek/закрытие и композицию с графом/деревом через
нынешний публичный API. Реализации списка, валидатора, staging builder, renderer
и package-деклараций/stubs нет. Это проверка доступности данных ядра, не native-
приёмка анимации стрелок, производительности или полная матрица будущего модуля.

Перед реализацией выбираем точные модель/входы/типы, атомарные trace-методы,
валидацию/ошибки, выдачу ID, границы staging, defaults проекции/null/routing,
приоритеты палитры и optional-адаптеры графа/дерева. Это решения новой возможности,
не обнаруженные причины менять Step/Frame/Scene перед 1.0.
