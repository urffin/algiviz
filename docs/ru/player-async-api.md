# Асинхронные источники в /player: API интеграции

[English](../player-async-api.md) · [Плеер](player.md) · [Адаптер](async-source-api.md) · [Поведение](async-sources.md)

## Кандидат 0.15.0, 2026-11-13

В рабочем дереве реализованы asyncSource, метаданные ожидания и closed в /player
через отдельный createAsyncSource. **В опубликованной 0.14.0 нет обеих асинхронных
возможностей.** Синхронные опции, запись и сигнатуры команд сохраняются.
Публикация и CI конкретного коммита — отдельно.

Третий взаимоисключающий источник — `asyncSource: AsyncSourceFactory<State>`.
Виджет сам создаёт адаптер и владеет им; готовый адаптер, итератор или promise
не принимаются. Конструктор фабрику не вызывает. Start и каждый фактический
Restart создают новые сеансы. Для ручного управления длительность необязательна;
`rewindCapacity` и `maxStepsPerFrame` сохраняют правила положительного безопасного
целого числа для обоих потоков. Запись требует длительности и запрещает оба
ограничения. У потока по-прежнему неизвестна длительность и нет ползунка времени.

## Публичные декларации

Декларации соответствуют [types.ts](../../src/player/types.ts) и публичному
классу Player. SharedOptions — приватное обозначение, не дополнительный экспорт.
Точка входа сохраняет runtime-экспорт Player и добавляет один публичный тип
PlayerCloseResult; типы отмены остаются в /playback.

Нужна ровно одна фабрика, отличная от undefined; явный undefined для остальных
веток допустим. Promise-фабрика запрещена: асинхронная инициализация выполняется
внутри итерации `AsyncIterable`. Вывод типов сохраняет State в render/frame.
Нынешние типизированные source/history и полные старые объекты подписей остаются
совместимыми. Новые поля статуса всегда присутствуют: собственные полные mock-
объекты `PlayerStatus` придётся дополнить. Новых значений phase/mode и асинхронных
render/status/error callbacks не добавляется.
Выбор/вызываемость фабрики и значения опций проверяются до вызова любой фабрики
или перемещения пользовательского viewport.

## Метаданные ожидания и подготовки

`phase` остаётся `idle | paused | playing | finished | error | disposed`,
`mode` — `stream | recording`. У async-потока `playing` означает намерение Play,
в том числе при остановленных часах из-за недоступных данных.
У sync/history на публичных границах waiting=false, preparing=null,
cleanupPending=false; canPause отражает текущее намерение Play.

- `waiting`: у основного сеанса есть запрос источника, результат которого ещё
  не обработан контроллером. При подготовке это запрос кандидата, а не
  изолированное старое чтение. Поле может оставаться истинным после Pause или
  Previous; это не прямое копирование getter waiting у адаптера.
- `preparing`: идёт Start/Restart, включая откат кандидата и ожидание очистки
  старого источника. Очищается после установки либо завершённого отката.
  `started` означает, что первый кадр хотя бы раз установлен; само принятие
  команды Start ещё не делает его истинным.
- `cleanupPending`: хотя бы один принадлежащий виджету источник начал закрытие,
  но ещё не завершил очистку. Может сочетаться с `waiting` при подготовке
  кандидата. Обычный запрос сам по себе не является очисткой. Поле блокирует
  новую фабрику после ошибки, но не запрещает готовое воспроизведение из окна
  пригодного сеанса.
- `canPause`: можно сбросить намерение Play, показа ожидающего ручного Next или
  автозапуска Replay. Остаётся истинным при Play без RAF в ожидании источника,
  может быть истинным в ручном режиме и при подготовке Replay. Ложно после
  сброса намерения, ошибки и dispose.

| Ситуация | phase | waiting | preparing | cleanupPending |
| --- | --- | --- | --- | --- |
| До Start | idle | false | null | false |
| Первый Start ожидает состояние | idle | true | start | false |
| Первый кадр установлен на паузе | paused | false | null | false |
| Play ждёт на границе потока | playing | true | null | false |
| Pause с тем же незавершённым запросом | paused | true | null | false |
| Готовое значение/EOF на паузе ещё не принято | paused | false | null | false |
| Restart ожидает кандидата | старая paused/finished/error | true | restart | возможно true |
| Кандидат готов, старый источник закрывается | старая paused/finished/error | false | restart | true |
| Первая подготовка неуспешна, кандидат закрывается | error | false | start | true |
| Ошибка активного сеанса, очистка ещё идёт | error | false | null | true |
| Dispose выполнен, физическая остановка ещё идёт | disposed | false | null | true |

Строки описывают реальную незавершённую работу: синхронная ошибка или закрытие
без ожидания могут пропустить промежуточную строку. До первого состояния нет
нового кадра/индекса/прогресса. Restart сохраняет старый кадр и окно до успешной
замены. Ошибка кандидата выставляет `hasError`, сохраняя старую фазу/сеанс.
Эта ошибка остаётся видимой при откате до следующего принятого действия,
сбрасывающего её по прежним правилам.

`waiting` не означает, что полезная работа целиком остановлена. После Previous
можно анимировать готовое окно при ожидающем запросе на прежней границе потока.
Часы останавливаются только когда нужное следующее состояние недоступно.
Сам приход результата не добавляет значение в окно, не вытесняет историю
и не двигает показанный индекс.

## Команды и доступность

Команды синхронны и возвращают текущий статус принятой команды, а не завершение.
Окончание наблюдается через `onStatus`/readonly getters; `await ui.start()`
или `await ui.restart()` не являются API ожидания готовности.

| Команда | Поведение async-потока |
| --- | --- |
| Start | Один начальный запрос, затем индекс ноль на паузе. Повторы объединяются; до первого кадра нет очереди Play/Next. После неудачной первой подготовки и очистки Start повторяет попытку. |
| Play | Требует длительности и пригодного подготовленного сеанса. Использует текущий запрос/готовый результат. Повтор идемпотентен. Ожидающий ручной Next становится намерением Play с таймером. Завершённый сеанс сам не перезапускается. |
| Next | Ставит на паузу без остатка времени. Завершает частичный переход без чтения; иначе берёт одно готовое состояние либо запрашивает одно. Отложенный ручной результат показывается с прогрессом 1. Повторы при этом чтении объединяются. Next при ожидающем Play меняет намерение на один ручной конечный кадр. |
| Pause | Сбрасывает намерение Play/ручного Next/Replay и остаток времени без закрытия адаптера. Результат начатого запроса занимает один готовый слот. Подготовка Start/Restart завершается на паузе. Pause безопасен и без текущего намерения. |
| Previous | Ставит на паузу и сразу двигается внутри окна, в том числе при незавершённом чтении. Поздний результат остаётся вне окна до достижения его границы при движении вперёд. Нет новой фабрики или отмены. |
| Restart | Ставит на паузу и готовит одного кандидата; повторы объединяются и сбрасывают автозапуск Replay. Сначала подготовка, затем аннулирование старого сеанса и ожидание его очистки до замены. Ошибка кандидата откатывается после его очистки. Автозапуска нет. |
| Скорость | Положительное конечное значение применяется к будущим интервалам, включая после подготовки. Допустимое изменение разрешено при подготовке; не отменяет запрос и не умножает время ожидания. |
| seek | По-прежнему недоступен обоим потокам. Запись сохраняет синхронный seek. |
| dispose | Сразу сбрасывает все намерения/подготовку, отключает управление и снимает UI-ресурсы. Источники закрываются отдельно; повторный dispose ничего не повторяет. Поздних render/status/error callbacks нет. |

При подготовке или ожидании очистки ошибочного сеанса применимые Play/Next/
Previous возвращают неизменённый статус без постановки в очередь. Прежние ошибки
возможностей/аргументов сохраняются: Play без длительности, seek потока,
Previous без перемотки, неконечная скорость. Pause и допустимая скорость доступны.
Start/Restart объединяются с текущей подготовкой и не обходят очистку новым
адаптером. Вызовы после dispose и изменения из render/status callbacks
по-прежнему отклоняются.

`canStart` требует отсутствия установленного кадра, подготовки/очистки для
восстановления и живого виджета. `canRestart` требует `started`, отсутствия
подготовки/очистки для восстановления и живого виджета. При подготовке оба ложны,
хотя программные повторы объединяются. `canPlay`/`canNext` требуют пригодного
незавершённого установленного сеанса без подготовки/восстановления; Play ещё
требует длительности. Они могут оставаться истинными при запросе: команда
переиспользует его или меняет намерение. `canPrevious` дополнительно требует
предыдущее значение в окне. У потока `canSeek` всегда ложен. После dispose
все возможности ложны.

Кнопка Replay с таймером — явное намерение «Restart, затем Play», а не изменение
программного `restart()`. После успешной подготовки/показа Play начинается,
только если намерение Replay актуально, документ виден и виджет жив. Pause,
программный Restart, ошибка, скрытие документа и dispose сбрасывают автозапуск.
После отмены Replay подготовка всё равно завершается на паузе.

При ожидании на границе потока остаток бюджета сбрасывается, часы останавливаются.
RAF для опроса не запускается. Результат Play планирует RAF, начинающий следующий
переход с прогресса ноль и новым отсчётом времени. Готовое окно использует прежние
часы/бюджет; запросы/EOF учитываются при начале, без повторного учёта при результате.
EOF и финальная пауза следуют поведенческому контракту без расходования времени
на Pause/ожидании. Скрытый документ ставится на паузу без автопродолжения;
reduced motion не добавляет чтений. Async-итерация не переносит CPU в другой поток.

## Подписи и доступное управление

Новые необязательные роли с английскими значениями по умолчанию:
`waiting: "Requesting state"`, `preparing: "Preparing playback"`,
`cleanup: "Waiting for source cleanup"`. Пропуск/undefined сохраняет значение
по умолчанию; явные значения — непустые строки. Полные старые `PlayerLabels`
допустимы, поскольку необязательны только новые роли. Старые обязательные роли
и частичные переопределения не меняются.

Play/Pause проверяет `canPause` раньше phase/Replay. Поэтому Pause виден и доступен
при ожидающем ручном Next даже без длительности шага и при подготовке Replay.
Иначе Replay предлагается только при finished/таймере и доступном Restart;
обычный Play следует `canPlay`. Новой кнопки Cancel нет. Подготовка/очистка
сохраняют отключённые элементы видимыми и закрепляют панель; один фоновый запрос
данных сам по себе overlay не закрепляет.

Сохраняются сводка phase/шага и значок потока. Метаданные сообщаются отдельным
вежливым live-статусом с приоритетом: очистка, подготовка, запрос источника.
Они не заменяют фазу и не объявляются на каждом RAF. `aria-busy` сцены означает
подготовку либо реальную остановку из-за данных, а не просто фоновый запрос
при повторе окна. Render/status ограничены за RAF; `onStatus` также сообщает
принятые команды и изменения асинхронного состояния без опроса.

## Ошибки, dispose и отчёт closed

Асинхронная операционная ошибка останавливает планирование и сразу уведомляет
`onError`, до конца физической очистки. Каждая основная операционная ошибка
сообщается один раз; вторичные ошибки очистки/уведомлений остаются диагностикой.
Ошибки активного источника проявляются и на Pause.
Изоляция старого чтения и откат кандидата следуют поведенческому контракту.
Поздняя ошибка чтения не срывает замену; настоящие `cleanupErrors` срывают.
Аннулирование/закрытие передают адаптеру причины `"player:restart"`/
`"player:dispose"`. Фатальная ошибка потребителя закрывает с исходной ошибкой;
тип причины сигнала остаётся `unknown`. Прежняя доставка синхронных ошибок
source/history и исключений callbacks сохраняется.

`closed` — один стабильный promise на виджет в любом режиме, без отклонения.
Разрешается только после **логического dispose виджета**, закрытия всех источников,
финальных уведомлений и снятия DOM/слушателей/таймеров. EOF/ошибка его не завершают:
живой виджет может перезапуститься. Некооперативный источник может задержать его
навсегда. `dispose(): void` остаётся синхронным; прежние синхронные ошибки dispose
выходят после очистки UI и также фиксируются в отчёте. Асинхронные ошибки после
dispose идут только в отчёт.

- `sources` содержит отчёты async-адаптеров, находившихся у виджета при логическом
  dispose, включая уже завершённый текущий: сначала текущий/закрываемый, затем
  кандидат, максимум два. У sync/history массив пуст. Отчёты ранее освобождённых
  сеансов не накапливаются в журнал за всю жизнь виджета.
- `errorCount` считает ошибки очистки источников, уведомлений и снятия ресурсов
  за жизнь виджета; `firstError` хранит только первое такое событие. Каждый отчёт
  адаптера обрабатывается один раз: ошибка очистки считается один раз, даже если
  отчёт также попадает в `sources`. Исходные source/render-ошибки уже сообщены
  как операционные и повторно не считаются; throw onStatus считается ошибкой
  уведомления, даже когда он является основной ошибкой операции. Поздние ошибки
  чтения — диагностика, а не сбои очистки или новые ошибки.
- Исключения асинхронного уведомления записываются без рекурсивного `onError`
  и ненаблюдаемого отклонения. Синхронное поведение сохраняется, как выше.
  Хранятся одна обёртка ошибки и счётчик вместо всей истории уведомлений.
- Отчёт/массивы/обёртки неизменяемы; пользовательские ошибки/причины не копируются.
  Финальные уведомления и снятие UI выполняются во время синхронного dispose;
  последующие асинхронные результаты не вызывают callbacks и изменений UI.
  Readonly `status.cleanupPending` может стать false при завершении закрытия,
  без нового уведомления; окончание наблюдается через `closed`.

## Проверка деклараций на этапе проектирования

Проверить вывод типов, взаимоисключение и явный undefined, старые опции/полные
подписи, прежние phase/mode/сигнатуры, сужение новых статусов/отчётов и readonly
в NodeNext/Bundler со строгими DOM-потребителями. Headless-импорты должны остаться
без DOM. Проверка деклараций не подтверждает поведение.

До реализации, 2026-11-13, TypeScript 6.0.3 прошёл четыре проверки в памяти: NodeNext и Bundler
с проектом DOM-деклараций, нынешним потребителем виджета и позитивными/негативными
async-сценариями; оба режима также прошли прежний headless-потребитель только
с ES2022 без ambient-типов DOM/Node. Проверены старые типизированные опции/подписи,
явный undefined в labels, вывод async State, взаимоисключение фабрик, синхронные
команды и readonly-отчёт. Блоки деклараций EN/RU совпадают. Файлы не генерировались,
runtime-код не менялся.

Будущие runtime-проверки: первое ожидание/кандидат, объединение команд и смена

## Реализация и проверки

Отдельные async-контроллер/сеанс сохраняют синхронный движок. Готовые состояния
хранятся в ограниченном окне Map и одном ещё не принятом результате чтения.
Логический dispose отделён от закрытия источников/UI. Диагностика хранит
счётчик/первую ошибку за жизнь виджета и максимум два отчёта источников при dispose.

Прошли все **265 тестов репозитория**, включая **21 тест публичного async-виджета**
с управляемыми promise и детерминированным планировщиком. Те же 21 тест прошли
из свежей установки локального npm-архива со строгой проверкой отклонений promise.
Потребители NodeNext/Bundler прошли TypeScript 5.0.4 и 6.0.3 с одним ES2022 без DOM/Node,
а также DOM-код, вывод State, readonly-статусы/отчёты и недопустимые опции.
Приватные пути закрыты; изоляция browser ESM bundles проверена.

[Нативный отчёт](../benchmarks/player-async-browser-2026-11-13.json) фиксирует
**13/13** проверок во встроенном браузере при DPR 1: DOM-кнопки/live-подписи,
ручной Pause, готовый результат, Restart/откат и отложенное закрытие, а также
Enter для Start/Next/Pause. Двенадцать проверок выполняет страница, тринадцатая
фиксирует отдельно выполненную клавиатурную последовательность. Одна ошибка
кандидата вызвана специально; неожиданных ошибок/отклонений нет. Хеши исходников,
сборки и страницы совпадают. Это локальные проверки, не сертификация браузеров,
не проверка звука screen reader, не публикация и не CI нового коммита.
