# Память и производительность

[README](../../ru/README.md) · [English](../performance.md)

## Память и стоимость генерации

Операции массива копируют входные данные, проверяют конечность чисел и отвергают
разреженные массивы. `defineArrayAlgorithm` делает это при первом `next()` итератора,
а `createArrayTrace` — сразу. Каждый итератор владеет своим рабочим состоянием.
Шаги массива, события, снимки и элементы заморожены; неизменяемые элементы могут
быть общими у нескольких снимков.

Воспроизведение генератора сохраняет соседние снимки, а не всю историю. Поэтому для
массива требуется O(n) памяти снимков, если вызывающий код не хранит старые кадры.
Произвольные состояния и внутренние структуры алгоритма могут иметь другую стоимость.
Каждый полный снимок массива всё равно копирует n позиций: ленивость уменьшает
хранимую историю, а не стоимость каждого шага. Сбор всех шагов возвращает затраты на
историю. Например, трасса квадратичной сортировки со снимками размера O(n) может
потребовать O(n³) времени и памяти истории. Итерация синхронна и может блокировать UI.

## Проверки производительности

Запустите `npm run benchmark` для массивов из 2 000 элементов: сортировки вставками,
пузырьком, слиянием и оба варианта быстрой сортировки. Отчёт показывает генерацию
1 000 шагов, медиану CPU-времени отрисовки по пяти выборкам из 100 кадров и занятую
кучу Node после каждых 5 000 шагов до 25 000. Canvas заменён заглушкой: это сравнение
CPU, а не измерение FPS браузера или GPU. Замеры кучи используют явную сборку мусора
и включают процесс Node; это диагностика, а не универсальные пороги прохождения теста.

## Профилирование реальных примеров

Команда `npm run benchmark -- --profile --output profile-node.json` измеряет
реальные генераторы сортировок вставками/слиянием, BFS, Boids и песка, проекции,
сопоставление объектов, диспетчеризацию и рендереры. В Node используется заглушка
Canvas со счётчиками. Для нативного Canvas сначала соберите пакет, запустите
локальный HTTP-сервер из корня репозитория и откройте `test/profile-browser.html`.
Нажмите кнопку запуска; полный JSON находится в раскрывающемся блоке. Import map
подключает локально собранные публичные точки входа. Отладка внешнего браузера
для этого не нужна.

Ограниченное окно диагностики выбирает соседние состояния из префикса источника
и проверяет восемь промежуточных кадров на пару. Полная трасса не собирается.
Серии замеров продолжают проход по окну, а не начинают каждый раз с первого кадра.
Генерация отдельно измеряет свежий префикс из 16 состояний, включая запуск.
Записываются семь выборок, прогрев, адаптивный размер серии, индексы и окружение.
Этапы пересекаются: время рендерера уже включает проекцию и сопоставление. Их нельзя
складывать или вычитать как точную разбивку затрат. Повтор команд Canvas сначала
проверяется побайтным сравнением пикселей одного кадра на сценарий. Оба режима
измеряют CPU и отправку команд, а не FPS, завершение GPU или универсальные пороги.
Запускайте замеры последовательно, отдельно от тестов и сборки.

См. [базовые замеры 0.13.0 и приоритеты оптимизации](performance-baseline-0.13.0.md).

## Проверка кэша сопоставления сцены

Команда `npm run benchmark -- --scene-cache --output scene-cache.json` сравнивает
CPU с реализацией /scene из релиза 0.13.0, взятой из локального Git. Скрипт
транспилирует этот исходник во временный модуль имеющимся TypeScript; ничего
не скачивается и не устанавливается. Релизный коммит должен быть в локальной
истории. Обе реализации работают в одном процессе на одних сценах настоящих
примеров; порядок замеров чередуется. Сначала сравниваются вычисленные кадры,
затем скорость повторной пары, интерполяции, смены пар и вызова без кэша.
Память проверяется на 4 000 парах с явной GC и WeakRef. Куча включает процесс
и служит диагностикой, а не универсальным порогом. См. [результаты и время
жизни кэша](scene-cache-performance.md).
