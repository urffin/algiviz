# Будущий /tree: эскиз контракта и совместимость с ядром

[English](../tree-contract.md) · [Эскиз графа](graph-contract.md) · [Сцены](scene.md) · [Совместимость](api-compatibility.md)

**Архитектурная проверка 2026-11-16; без реализации и публикации.** Проверен
кандидат a9b93f8. Пакет не экспортирует /tree и /graph. Имена и формы ниже —
эскиз будущего модуля, не текущие экспорты или окончательные сигнатуры.
Существующие примеры дерева и кучи остаются кодом приложения.

## Вывод и объём

Предлагаемая модель укладывается в нынешние Step, Frame, Scene, generic registry
и Player. Менять восемь существующих entry или их закрытые unions для этого
объёма не требуется. Будущий экспорт /tree сам добавит публичный API; совместимое
добавление может быть minor-возможностью по U3. Сейчас новый entry не добавляется.
В указанном объёме блокер ядра перед 1.0 не найден.

Первый объём — конечное **корневое упорядоченное дерево**, включая пустое.
Снимки могут атомарно описывать вставку, удаление поддерева, смену родителя,
порядка соседей и повороты. Это требования к представимости данных, а не выбор
методов изменения или обещание встроенного алгоритма поворота. Алгоритм и
построение последовательности снимков принадлежат приложению до отдельного
проектирования trace API.

Лес можно составить из независимо именованных деревьев в одной сцене. DAG,
общий ребёнок у нескольких родителей, циклы и произвольные графовые рёбра вне
модели дерева. Свойства BST, балансировки и кучи, сравнение ключей, обходы и
автоматическая балансировка — политики алгоритмов. Общее упорядоченное дерево
не подразумевает бинарные left/right-слоты: для пропущенного бинарного ребёнка
нужна отдельная явная политика, а не догадка по отсутствующему соседу.

## Модель, корректность и владение

Снимок концептуально содержит:

```text
rootId: ID узла | null
nodes: записи со стабильным ID и прикладными label/data
links: записи со стабильным ID, parentId и childId
layout: ID узла -> конечные x/y
annotations: ID узла/связи -> постоянные role/data
result: выбранные ID узлов/связей либо нет результата
```

Это модель, не экспортированные TypeScript-интерфейсы. Порядок связей, выбранных
для одного родителя из общего списка, задаёт порядок детей. Порядок хранения
узлов не является порядком детей. Представление одно авторитетное: индексы
parent/children/depth, если появятся, вычисляются из него и не могут независимо
ему противоречить. Синтаксис входа, defaults, accessors и порядок валидации/ошибок
остаются задачей следующего контракта публичного API.

Инварианты каждого зафиксированного снимка модели:

- ID узлов и связей — непустые примитивные строки, уникальные в своих наборах.
  Подпись, значение, индекс, глубина и порядок детей не являются ID.
- Пустое дерево имеет rootId: null и пустые nodes/links. Непустое имеет один
  существующий корень без входящей родительской связи.
- Каждый другой узел имеет ровно одну входящую связь. Концы существуют; петли,
  дубли parent-child, несколько родителей и циклы недопустимы.
- Все узлы достижимы из корня. Отключённые скрытые узлы не образуют второе
  неявное дерево: видимость отличается от принадлежности модели.
- Аннотации/результат ссылаются на текущие ID нужного набора. Раскладка даёт
  необходимые проекции позиции с конечными координатами.

Будущий модуль проверяет обновление целиком до фиксации данных и выдачи шага.
Перенос к потомку недопустим. Удаление включает затронутые связи и аннотации/
результат; удаление корня либо даёт пустое дерево, либо атомарно задаёт новый
корень и корректную иерархию. Поворот выдаёт корректные снимки до/после, не
выставляя временные некорректные мутации. Будущий валидатор здесь не реализуется
и его корректность этой проверкой не подтверждается.

Собственные записи/коллекции модуля копируются и замораживаются в неизменяемых
снимках; неизменившиеся части могут разделяться. Неизменяемость прикладного
payload и Worker-cloneability обеспечивает приложение. Freeze для Map/Set не
замораживает содержимое. Автоматическое глубокое копирование произвольного
payload не обещается ни эскизом, ни общим playback.

## Связь с /graph

Оба эскиза используют стабильные ID узлов/связей, неизменяемые аннотации/результат,
пространства имён сцены, чистую проекцию и ссылки через scene.get. Явный ID связи
дерева удовлетворяет требованию графа об отдельном ID ребра. Не следует получать
идентичность из пары parent-child: при смене родителя она меняется.

Снимок дерева можно представить данными графа: nodes переходят в nodes, links —
в направленные рёбра от родителя к ребёнку с теми же доменными ID. Корень и
порядок детей остаются метаданными дерева: общий граф их не подразумевает.
Произвольный граф нельзя принять как дерево без проверки всех его инвариантов.

Первый эскиз /graph специально фиксирует топологию на trace. **Меняющееся дерево
нельзя передавать будущему graph trace с фиксированной топологией или неявно
расширять его контракт.** Изменения дерева выражаются собственным State и
нынешним generic playback/scene. Общее будущее внутреннее рисование не требует
публичного наследования, зависимости или расширения закрытого GraphEvent.
Обоих модулей пока нет; точные зависимости/адаптеры не выбраны.

Виды сцены дерева условно названы treeNode/treeLink; имена графа тоже пока
предварительные. Геометрию можно разделять, но graph registry автоматически
не становится tree registry. Составной прикладной registry может содержать оба.
Новых обязательных видов у существующих registry или будущего graph type-map
не появляется. Проекции нужен заранее выбранный стабильный набор видов, а не
его расширение с каждым алгоритмом. Декорации добавляются приложением.

## Шаги, кадры и управление

```ts
// TreeState/TreeEvent здесь — прикладные типы, не экспорты пакета.
type TreeStep = Step<TreeState, TreeEvent>;
type TreeFrame = Frame<TreeState, TreeEvent>;
```

Корень, иерархия, постоянные отметки и результат находятся в State. Event описывает
операцию; renderer не должен восстанавливать иерархию по истории событий.
Очередь, стек, рекурсивные вызовы, сравнения и порядок обхода при необходимости
остаются в прикладном состоянии. Ролям нужно явно открытое расширение либо
типизированный payload; ArrayEvent и фазы Player не меняются.

createStepEmitter, createPlayer/createTimeline и Player stepSource/isTerminal
уже передают эти типы. Финальная работа выполняется до terminal yield, очистка —
в finally. Pause, Next, final hold, Restart и dispose сохраняют текущие правила.
Restart получает свежий источник из фабрики с исходным корнем/иерархией без
прежнего результата. Previous восстанавливает сохранённые снимки, не запускает
обратные повороты. Окно перемотки использует позиции последовательности, не ID
узлов, глубины или step.index.

State-only asyncSource/Worker остаются применимы с завершением по EOF и undefined
event. Постоянная визуализация не может требовать Frame.event. Async explicit
events/terminal predicates — отдельная возможность playback, не новая ветка
PlayerOptions для деревьев. Plain model data допускает structured clone;
исполняемые алгоритмы/handlers не передаются как данные.

## Идентичности, изменения иерархии и раскладка

Scene ID различают деревья, графы, узлы, связи и несколько представлений одной
сущности. Tuple-кодировка из эскиза графа — безопасный пример, не обещанная
публичная кодировка интеграции. Для дерева/массива кучи можно разделять доменный
ID элемента, но каждой видимой копии нужен собственный scene ID.

ID узла сохраняется при смене позиции, родителя, подписи и статуса корня. Новая
логическая сущность получает новый ID даже при равном значении. Связи тоже имеют
явные логические идентичности: связь может менять концы, а удаление и замена
отношения могут использовать новый ID. Будущий trace API должен выбрать правила
выдачи/сохранения ID. Изменение концов не означает смену scene type или
автоматическое сопоставление по паре концов.

Кадр поворота предоставляет оба корня/иерархии через previous/current State.
Переходы сцены сохраняют позиции узлов и старые/новые ссылки связей. При смене
концов handler должен разрешать **оба поколения** через scene.get: чтение только
current может дать скачок. Интерполяция или crossfade двух геометрий связи — ещё
не выбранная политика renderer. Новые relation/parent-поля Frame/Scene не нужны.

Корректными деревьями обязаны быть зафиксированные снимки. Промежуточная геометрия
анимации не является третьей топологией; возможны пересечения/наложения. Ядро
не обещает автоматический morphing или отсутствие пересечений. При совместном
исчезновении узла/связи scene.get сохраняет старые переходы концов даже при
нулевом presence; вставка использует новые концы. SVG/DOM с сохранением элементов
сверяет нарисованные ID каждый кадр: seek может пропустить exit-callbacks.

Раскладка детерминирована неизменяемой моделью/политикой вида и не зависит от
истории render. Позиции находятся в State либо вычисляются чистой проекцией с
неизменяемой захваченной политикой. Она может учитывать иерархию/порядок детей;
viewport/DPR-преобразование применяется в handlers одинаково к узлам и связям.
Смена захваченной политики требует нового projector. Mutable DOM и раскладке,
зависящей от progress, не место в endpoint-cache createSceneProjector.

Сворачивание/фильтрация, если появятся позже, требуют неизменяемого view state,
отдельного от состава модели. В сцену попадают только связи с отображаемыми
концами. scene.get не даёт объект, отсутствующий в обеих endpoint-сценах.
Выбранный скрытый узел остаётся данными модели; сводная отметка — будущая политика
вида. Маршрут указателя через предков относится к приложению/renderer, не
управлению playback. Нынешний пример указателя не обещает маршрутизацию через
произвольно меняющуюся топологию.

## Проверка и оставшиеся решения модуля

| Потребность | Нынешний механизм | Изменение ядра |
| --- | --- | --- |
| Корень, порядок детей, ограничения дерева | Generic State; валидация модуля | Нет |
| Вставка/удаление/смена родителя/повороты | Стабильные ID, enter/update/exit | Нет |
| Движение узлов и смена концов связей | ObjectTransition + progress + scene.get | Нет |
| Результат, rewind, seek и свежий Restart | Неизменяемый State, playback и Player | Нет |
| Граф/дерево/массив в одной сцене | Namespaces и составной generic registry | Нет |
| Canvas или SVG с сохранением элементов | Независимые handlers, сверка приложения | Нет |
| Async/Worker-состояния | Прежние state-only-контракты | Нет |

Изолированная проверка прошла **31/31 runtime-сценариев** и четыре strict-
конфигурации TypeScript 6.0.3: NodeNext/Bundler × headless ES2022/Player DOM.
Девять отрицательных tree type-cases проверяют readonly, narrowing, события и
registry. Runtime использует рукописные прикладные состояния/сцены и прежние
примеры дерева/кучи с публичным ядром установленного кандидата. Реализации /tree,
валидатора модели, layout solver и новых package-деклараций/stubs нет.
Проверка подтверждает доступность данных, не качество нативной отрисовки,
маршрутов, стоимость кадра или полную матрицу совместимости будущего модуля.

Перед реализацией нужно выбрать экспорты/входные типы, ошибки/валидацию и
атомарные trace-методы, выдачу ID связей, границы binary slots/леса, API и пределы
раскладки, приоритеты палитры, optional-загрузку renderer и graph interop.
Модель дерева должна остаться headless и DOM-free; новых rendering-импортов в
нынешние headless-entry не требуется. Гарантии производительности требуют
отдельных workloads.

Это решения новой возможности, а не найденные изменения Step/Frame/Scene,
необходимые перед 1.0. Более широким требованиям нужна отдельная ревизия.
