# Будущий /graph: эскиз контракта и совместимость с ядром

[English](../graph-contract.md) · [Сцены](scene.md) · [Playback](../playback.md) · [Политика совместимости](api-compatibility.md)

**Следующий этап, 2026-11-17:** [контракт публичного API](graph-api.md) выбирает
типы trace/модели, отметки/результаты, валидацию и отдельный `/canvas/graph` на
базе выпущенной 1.0.0. Headless `/graph` реализован локально, без публикации;
`/canvas/graph` тоже реализован локально. Этот эскиз от 2026-11-16
и его проверки сохраняют исторический объём; отложенные решения API ниже
заменяются явно выбранными решениями следующего этапа.

**Архитектурная проверка 2026-11-16; без реализации и публикации.** Текущий
кандидат — a9b93f8. Пакет не экспортирует /graph, graph trace, графовые события
или штатный графовый renderer. Имена и наброски ниже относятся к будущему
модулю, не к доступным декларациям. Примеры графа/DFS/дерева остаются кодом
приложения.

## Вывод и первый объём

Описанный модуль укладывается в нынешние Step, Frame, Scene, диспетчеризацию
сцен и Player. Его можно добавить отдельной возможностью, не меняя нынешние
восемь entry и не расширяя их закрытые unions. Будущий /graph сам добавит
публичный API, обычно как minor-функция по U3; сейчас девятый entry не добавляется
и реализация не поручается.

Для этого первого объёма блокера ядра перед 1.0 не найдено. Это ограниченный
архитектурный вывод, а не готовый проект любого будущего редактора/раскладки
графа и не замена приёмки реализации.

Первый объём:

- Фиксированная конечная топология на trace: явно заданные вершины и рёбра со
  стабильными ID. Допустимы несвязные компоненты, пустой граф и граф без рёбер.
- Самостоятельный ID ребра позволяет петли и параллельные рёбра. Направление
  и необязательный конечный вес — данные графа, не playback. Без направления
  ребро неориентированное; направление может задаваться на уровне ребра.
  Нулевые/отрицательные веса не запрещены моделью: ограничения выбирает алгоритм.
- Неизменяемые визуальные аннотации, выбранные вершины/рёбра результата и явное
  завершение. BFS/DFS/Dijkstra, очередь, стек, расстояния и порядок обхода
  принадлежат приложению. Модуль не вычисляет алгоритм или путь автоматически.
- Проекция в объекты вершин/рёбер. Возможное штатное рисование отделяется от
  headless-модели, как сейчас /array отделён от /canvas.

Редактор топологии, физический движок, автоматическая async-раскладка, встроенные
алгоритмы и распределённое состояние вне первого объёма. Явное изменение
раскладки уже выражается обычными неизменяемыми снимками.

## Модель и владение

Лексика входа следует нынешнему примеру графа: nodes с id/label и edges с
id/from/to; при необходимости направление/вес. Порядок входа сохраняется.
Playback не выбирает порядок соседей и не сортирует adjacency. Формат
vertices/source/target в примере DFS — другая прикладная модель; он не обязан
меняться, пока сам пример не решит перейти на новый модуль.

ID вершины/ребра — непустая примитивная строка, уникальная в соответствующем
наборе. Подпись и позиция не являются идентичностью. Концы каждого ребра
существуют в снимке. ID ребра не выводится из пары концов: параллельные рёбра
должны иметь разные ID даже при совпадении остальных данных.

Модуль копирует свои структурные записи/коллекции аннотаций и выдаёт неизменяемые
снимки. Постоянную топологию можно разделять между ними. Неизменяемость и
Worker-cloneability прикладного payload остаются ответственностью приложения.
Object.freeze(Map/Set) не делает их содержимое неизменяемым; для собственных
данных предпочтительны plain records и readonly-массивы.

Набросок состояния:

```text
graph: nodes[] + edges[]                 неизменяемая топология
layout: ID вершины -> конечные x/y       позиции в снимке
node/edge annotations: ID -> role/data  постоянное визуальное состояние
result: ID вершин и рёбер либо нет       явно выбранный ответ
```

Это набросок, не окончательные публичные интерфейсы. Очередь, стек, predecessor
и distance могут оборачивать/дополнять графовый снимок в прикладном State.
Новых полей общего Frame не требуется. Отсутствие пути — обычный результат
алгоритма в State, не новая фаза Player или ошибка источника.

Аннотации и принадлежность результату хранятся в State, не только в последнем
Event. Поэтому seek/rewind/repaint детерминированы, а финальный путь сохраняется
без памяти renderer, как resultItemIds массива. Sorted-поля массива не используются.
Для визуальных ролей нужно явно открытое расширение либо типизированный
прикладной payload, а не глобальный закрытый список состояний всех алгоритмов.
Точные роли и палитра относятся к следующему контракту API модуля.

Изменения/отметки проверяются до фиксации собственных данных и выдачи шага.
Точные constructor/trace-методы, input/output-типы, порядок ошибок и классы
ещё требуют отдельного проектирования публичного API. Эскиз не вводит новых
обещаний в существующие playback/scene.

## Шаги, кадры и управление

Используем нынешние типы напрямую:

```ts
// GraphState и GraphEvent здесь — прикладные типы.
type GraphStep = Step<GraphState, GraphEvent>;
type GraphFrame = Frame<GraphState, GraphEvent>;
```

State содержит граф и аннотации алгоритма. Event остаётся generic: нынешний BFS
завершается kind: 'finished', DFS — type: 'done'. Оба работают с явным predicate.
Возможные удобные createGraphTrace/graphScene — ориентиры будущего API;
их точные экспорты/сигнатуры пока не выбраны. ArrayEvent расширять нельзя.

createStepEmitter, createPlayer/createTimeline, ограниченная перемотка и Player
stepSource уже подходят. Player получает свежую фабрику и isTerminal для своей
модели событий. Владение источником, терминальное время, подготовка Restart
и dispose сохраняют нынешние правила. Финальная работа алгоритма выполняется
до терминального yield, очистка — в finally.

Previous и seek читают сохранённые состояния, не исполняют алгоритм назад.
Restart создаёт новый trace без прежних аннотаций/результата. ID — идентичности
внутри trace, а не изменяемые объекты между перезапусками. Правила step.index/
времени прежние; ID графа не связаны с индексами шагов и позициями окна.

Async/Worker уже передают произвольный Graph State через asyncSource. Эта ветка
остаётся state-only с завершением по EOF: рисование графа не должно требовать
определённого Frame.event. Постоянные аннотации находятся в State. Async explicit
steps/terminal predicates — отдельная возможность playback, не неявная новая
ветка PlayerOptions, которую потребует /graph.

## Идентичности сцены и геометрия

Сцена графа имеет два стабильных встроенных вида, условно graphNode и graphEdge.
Точные имена type-map отложены. Подписи можно рисовать внутри этих handlers.
Собственные декорации добавляются прикладным расширенным registry. Новый
обязательный встроенный вид позже сломал бы пользовательские registry по U3;
такого расширения следует избегать.

Scene ID уникален во всей составной сцене, даже если у вершины и ребра одинаковый
доменный ID A или несколько графов используют одинаковые подписи/ID. Безопасный
ориентир — JSON.stringify([namespace, 'node', nodeId]) и аналогичный ключ ребра.
Это не создаёт коллизий из разделителей/кавычек. Точную кодировку необязательно
делать публичным способом интеграции приложения.

Data ребра хранит ссылки на **scene ID вершин**, а не угаданные позиции массива
или текущие координаты. scene.get возвращает переход вершины со старыми/новыми
данными и выходящими объектами. Рёбра обычно ниже вершин, декорации выше;
нового поля отношений или zIndex не требуется.

Движение вершины — интерполяция её позиций из endpoints по progress. Ребро
использует те же интерполированные позиции. Если модель допускает смену концов
ребра, handler должен учитывать старые и новые ссылки; использование только
текущего конца было бы ошибкой реализации, не отсутствием данных в ядре.
Петли требуют кривых, параллельные рёбра — детерминированных полос, привязанных
к ID/порядку рёбер. Это работа графового renderer, не Frame или matching сцен.
Формулы и стандартная раскладка здесь ещё не выбраны.

В каждом снимке концы корректны. При будущем редактировании ребро и вершина
могут исчезнуть вместе: scene.get ещё предоставляет старый переход вершины
для выходящего ребра. Enter/exit уже есть. Dangling edges, смена scene type
под прежним ID и повтор ID для другой сущности — ошибки модели/идентичности.
Замена сущности требует нового ID; seek может пропускать промежуточные состояния.

Проекция — чистая функция неизменяемого State. Нельзя читать progress, изменяемый
размер Canvas, globals алгоритма или живой DOM в createSceneProjector. Позиции
содержатся в State либо неизменяемой захваченной раскладке; renderer отображает
их в текущий viewport одинаковым преобразованием для обоих endpoints. Смена
захваченных namespace/layout policy требует нового projector. Прежние кеш двух
endpoints и владение viewport/DPR приложением сохраняются.

## Сопоставление с нынешним API

| Потребность | Существующий механизм | Изменение ядра |
| --- | --- | --- |
| Вершины, ориентированные/взвешенные/параллельные рёбра, петли | Произвольные State/data и разные scene ID | Нет |
| Очередь/стек/distance/current/result | Прикладной State и собственный registry | Нет |
| События графа | Generic E в Step/Frame и терминальный predicate | Нет |
| Движущиеся вершины и связи | Endpoints ObjectTransition, progress, scene.get | Нет |
| Seek/rewind и сохраняемый ответ | Неизменяемый State, projector и аннотации current | Нет |
| Завершение, hold, закрытие, Restart/dispose | Общие headless-плееры и Player stepSource | Нет |
| Canvas/SVG | Независимые от backend handlers и свой context | Нет |
| Будущие enter/exit топологии | Missing endpoints и presence | Нет; вне первого объёма модуля |
| Async-состояния графа | Прежние asyncSource/Worker, event может быть undefined | Нет |

## Проверка и оставшиеся решения модуля

Проверка использует **рукописные прикладные состояния/сцены**, нынешние публичные
функции и существующие BFS/DFS-примеры. Graph builder, layout, adapter или
штатный renderer не реализуются. Изолированные strict type-пробы проверяют
State/Event и обработчики graphNode/graphEdge без объявления нового package
module. Runtime-пробы проверяют ссылки, ID, слои, параллельные рёбра, петли,
enter/exit, проекцию, seek, закрытие и прежние источники примеров. Это проверка
возможностей ядра, не тесты ещё отсутствующего /graph, не визуальная проверка
кривых и не новое native-свидетельство релиза.

Перед реализацией /graph остаётся выбрать точные экспорты, модель/defaults,
расширяемость trace/event, валидацию/ошибки, приоритеты цветов и routing/layout API.
При штатном renderer нужна собственная граница optional-загрузки/деклараций:
/graph должен остаться headless и DOM-free, например с отдельным graph-rendering
entry либо другим явно выбранным разделением. Новых rendering-импортов в
существующие headless-модули быть не должно.

Это решения новой возможности, а не найденные причины переделывать Step/Frame/
Scene до 1.0. Если новые требования потребуют изменения нынешних контрактов,
нужна отдельная ревизия совместимости, а не автоматическое объявление minor.

Изолированная проверка дала **25/25 runtime-сценариев нынешнего ядра** и четыре
успешные strict-конфигурации TypeScript 6.0.3: NodeNext/Bundler × headless
ES2022/DOM. Это не полная матрица компиляторов нового модуля и не native-проверка.
