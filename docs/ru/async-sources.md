# Асинхронные источники состояний: контракт

[English](../async-sources.md) · [План развития](../optional-player-proposal.md) · [Плеер](player.md)

Отдельный [контракт Worker-транспорта](worker-source.md) от 2026-11-14 определяет
владение/сериализацию и кооперативную, затем принудительную остановку в 0.16.0.
[Подключение к Player](player-worker.md) использует прежний asyncSource
с сохранением общего async-контракта. Обычный асинхронный
источник этот адаптер по-прежнему не может прервать принудительно.

## Объём этапа, 2026-11-13

Контракт охватывает отдельный адаптер и интеграцию с виджетом, опубликованные
в 0.15.0. См. [проверку релиза](../releases/0.15.0.json). Разделы
Start/Pause/Restart и RAF ниже описывают поведение виджета; у адаптера
используются next/dispose по его публичному API.

Первый асинхронный вариант принимает `AsyncIterable<State>` с неизменяемыми
состояниями, включая источники помимо асинхронных генераторов. Итерацией владеет
отдельный headless-адаптер; подключение к `/player` доступно в 0.15.0. Существующие
синхронные фабрики, возвращаемые типы, доставка ошибок и headless-импорты сохраняют
совместимость. Запись остаётся синхронным массивом.
Render и callbacks уведомлений остаются синхронными; асинхронные рендереры
не входят в этот контракт.
Отдельный [проект публичного API и типов адаптера](async-source-api.md) теперь
определяет имена экспортов, сигнал отмены, результаты чтения и отчёт очистки.
[Проект API интеграции с виджетом](player-async-api.md) теперь определяет опции
источника, метаданные ожидания/подготовки, команды и очистку виджета.
Headless-декларации по-прежнему компилируются только с ES2022, без типов DOM/Node.

## Владение и запросы

- Конструктор не вызывает фабрику источника. Start получает новый приватный
  итератор и запрашивает первое состояние. Каждый перезапуск вызывает фабрику
  заново. Фабрика возвращает асинхронный iterable непосредственно; асинхронная
  инициализация выполняется внутри итерации, а не через promise самого iterable.
- Сеанс единолично владеет итератором. На один итератор допускается не больше
  одного незавершённого `next()`. Нет чтения вперёд, очереди команд Next,
  автоматического повтора или таймаута по умолчанию. Синхронный throw и отклонение
  promise одинаково считаются ошибками.
- До первого значения кадра нет. Start показывает его на паузе с индексом ноль.
  Следующие принятые состояния получают последовательные индексы; возвращаемое
  значение генератора игнорируется. Пустой источник — ошибка подготовки.
- Последнее значение само не сообщает о конце: дополнительный запрос обнаруживает
  `done`, сохраняя кадр и индекс. Финальная пауза начинается, когда воспроизведение
  на границе потока обрабатывает EOF; ожидание и EOF на паузе её время не расходуют.
- Состояния хранятся по ссылке, без копирования и заморозки. По умолчанию хранятся
  соседние кадры и не больше одного ещё не принятого результата. Перемотка добавляет
  только ограниченное окно; полная история не собирается.

## Ожидание и время воспроизведения

Ожидание независимо от намерения воспроизведения: запрос может выполняться как
при Play, так и на паузе. Будущий статус должен различать незавершённый запрос
источника и подготовку Start/Restart, включая ожидание очистки. Индикатор ожидания
не означает завершение или ошибку. До первого состояния нет индекса и прогресса.
При остановке из-за данных на границе потока показанный кадр сохраняется;
один фоновый запрос не останавливает воспроизведение готового окна.

На границе перехода Play запрашивает недоступное следующее состояние и
приостанавливает часы. Необработанное время, включая остаток бюджета за кадр,
сбрасывается; время ожидания не накапливается. Приход результата планирует RAF;
этот RAF начинает следующий переход с прогресса ноль и новой временной отсчётной
точки. Нет скачка, пропуска состояния или ускоренного наверстывания ожидания.
Прежнее ограничение дельты 100 мс и множитель скорости применяются только
к интервалам работающих часов.

RAF не запускается только ради проверки promise. Обработка результата сама не
начинает следующее чтение. Готовые значения окна используют прежний бюджет
за кадр. Чтение источника и проверка EOF учитываются при начале запроса; принятие
его результата повторно тот же запрос не учитывает. Шаги из окна считаются
по прежним правилам. Async-итерация не переносит вычисления в другой поток
и не позволяет прервать отдельный тяжёлый вызов источника, render или callback.

## Управление

| Действие | Выбранное поведение |
| --- | --- |
| Start | Один запрос первого состояния. Повторный Start во время подготовки объединяется с текущим. Play/Next/Previous недоступны до её завершения. Автозапуска нет. |
| Next | Ставит на паузу и сбрасывает остаток времени. Завершает частичный переход без чтения; иначе берёт состояние из окна/готового результата либо запрашивает одно. Асинхронный ручной результат показывается в конечной точке. Повторный Next во время этого запроса объединяется с ним, а не заказывает несколько шагов. |
| Pause | Отменяет RAF и намерение показать ожидаемый результат, сбрасывает остаток времени, но не отменяет источник и начатое чтение. Поздний результат занимает один готовый слот без смены кадра. Следующий Play/Next использует его. Подготовка Start/Restart всё равно завершается на паузе. |
| Play | Требует длительности шага и подготовленного сеанса. Использует существующий запрос или готовый результат без второго чтения. Ожидающий ручной Next становится намерением воспроизведения с таймером. Повторный Play ничего не добавляет. |
| Previous | Ставит на паузу и немедленно перемещается внутри окна, даже если на границе потока выполняется запрос. Его результат хранится вне окна, пока движение вперёд не достигнет границы и не примет значение. Сам приход результата не вытесняет историю и не меняет индекс. |
| Скорость | Меняет будущие интервалы часов, не отменяя чтение и не умножая время ожидания. |
| Скрытие документа | Действует как Pause; возвращение видимости не возобновляет Play. |
| dispose | Сразу отключает управление, аннулирует ожидаемый показ/подготовку, снимает слушатели и таймеры, сохраняет последний читаемый кадр. Запрашивает кооперативную отмену и асинхронную очистку. Повторный вызов не повторяет эти операции. |

Методы существующего виджета остаются синхронными: возвращаемый статус описывает
принятую команду, а не завершение асинхронной работы. Ошибка источника, пришедшая
на обычной паузе, всё равно завершает текущий сеанс с ошибкой. Seek для потока
недоступен. `pagehide` действует как dispose.

## Restart: подготовка, затем замена

1. Старый сеанс ставится на паузу без остатка времени; кадр и окно сохраняются.
   Создаётся один кандидат, ожидается его первое состояние. Повторный Restart
   во время подготовки объединяется с текущим, не создавая новых кандидатов.
   Остальные команды воспроизведения до конца подготовки недоступны; Pause,
   допустимая смена скорости и dispose остаются доступны.
2. Ошибка фабрики, получения итератора или первого запроса сообщается как ошибка
   подготовки и закрывает кандидата. Подготовка остаётся незавершённой до конца
   этой очистки; другой кандидат не может её обойти. Затем возвращается старый
   сеанс на паузе либо состояние ошибки без кадра, если старого сеанса не было.
   Start может повторить попытку после очистки. Результат/ошибка незавершённого
   старого запроса изолируются на время подготовки. При откате сначала сообщается
   ошибка кандидата, затем исход старого запроса применяется по обычным правилам:
   значение остаётся готовым, а собственная ошибка старого чтения независимо
   завершает восстановленный сеанс и сообщается один раз. Сам сбой кандидата
   не уничтожает пригодный старый сеанс.
3. После первого значения кандидата старый сеанс аннулируется и получает отмену.
   Только после завершения его очистки устанавливается и показывается первый
   кадр кандидата на паузе. До этого кандидат больше не читает источник. Ошибка
   закрытия старого итератора прерывает замену, закрывает кандидата и сохраняет
   последний читаемый кадр; аннулированный старый сеанс уже нельзя возобновить.

Ожидание очистки ограничивает владение одним старым сеансом и одним кандидатом:
брошенные итераторы не накапливаются с каждым Restart. Следствие: не реагирующий
на отмену старый источник может задержать Restart навсегда, даже если первое
новое состояние уже готово. Интерфейс остаётся отзывчивым, dispose доступен.
Dispose сразу прекращает показ, но не может принудительно остановить внутреннюю
работу источника. Ошибки уже аннулированного запроса не затрагивают новый сеанс.
Незавершённая очистка после предыдущей ошибки также должна закончиться до нового
вызова фабрики. Ограничение действует и на неудачную подготовку/восстановление,
а не только на успешные перезапуски. Логический dispose по-прежнему немедленный
и не означает завершения физической очистки.

## Отмена и очистка

Фабрика получает кооперативный сигнал отмены для своего сеанса. Pause и Previous
его не отменяют. Завершение подготовки кандидата с последующим закрытием старого
сеанса, фатальная ошибка и dispose отменяют. Отмена фиксируется до уведомления
источника, выполняется один раз и запрещает последующие чтения/показ этого сеанса.
Ошибка обработчика сигнала не мешает аннулированию и остальной очистке.

Если итерация не завершилась естественно, `return()` при его наличии запрашивается
не больше одного раза, **после завершения начатого `next()`**. Методы итератора
не выполняются одновременно. Все promise запросов и очистки наблюдаются даже
после аннулирования: поздние значения отбрасываются, отклонения обрабатываются.
Естественный `done` освобождает владение без дополнительного `return()`.
Каждый `next()` должен завершаться объектом результата итерации; некорректный
результат — ошибка источника. Для успешной очистки по этому контракту реализованный
`return()` должен завершиться с `done: true`. Нетерминальный/некорректный результат
return — ошибка очистки; адаптер не вычитывает значения, выдаваемые при закрытии.
Если `return()` отсутствует, освобождение возможно только через сигнал. Отчёт
очистки подтверждает завершение принадлежащих адаптеру вызовов, но не освобождение
произвольных внешних ресурсов.

Отмена не является принудительным прерыванием. Если источник игнорирует сигнал
и не завершает запрос, окончание очистки и Restart не гарантируются. Таймаут
и успешное закрытие не придумываются. Если требуется ограниченное время остановки,
ресурсы источника должны реагировать на отмену.

Логический dispose отделён от физического завершения очистки. Асинхронный адаптер
и виджет должны предоставлять ожидаемый результат очистки, завершающийся только
после всех принадлежащих им запросов и закрытия. Он успешно разрешается с отчётом,
включая ошибки очистки, а не создаёт ненаблюдаемое отклонение. Существующий
`dispose(): void` не становится promise. Финальное уведомление disposed может
выполниться синхронно; позже render/status/error callbacks уже не вызываются.
Поздние ошибки доступны в отчёте очистки, а не в callbacks после dispose.

## Ошибки и порядок гонок

- Ошибки фабрики, получения итератора и пустого источника следуют правилам
  подготовки/отката. Поздняя ошибка активного источника фатальна: пауза,
  сохранение читаемого кадра, аннулирование сеанса, запрос очистки и однократная
  доставка исходной ошибки. Автоповтора нет; восстановление — новый Start/Restart.
- Ошибки источника, render и status-callback имеют приоритет над ошибками
  вызванной ими очистки. Вторичные ошибки сохраняются в диагностике очистки.
  Самостоятельная ошибка очистки сообщается как таковая; сбой кандидата не
  уничтожает пригодный старый сеанс. Ошибки уведомлений не отправляются
  рекурсивно в `onError`.
- Отмена владельцем — нормальное управление. Отклонение активного источника
  с именем `AbortError` остаётся ошибкой, если сеанс действительно не был отменён;
  одного имени ошибки недостаточно.
- Команды и результаты обрабатываются последовательно с проверкой идентичности
  сеанса и актуального намерения показа. Pause до обработки результата запрещает
  его показ; dispose до обработки запрещает все поздние callbacks. Кадр, принятый
  до Pause, остаётся видимым. Откат Restart возвращает только сохранённый старый
  сеанс, но никогда не аннулированный.
- Promise запроса headless-адаптера отклоняется с основной ошибкой операции.
  Виджет наблюдает асинхронные ошибки и сообщает их через статус/onError;
  ошибки асинхронного уведомления попадают в диагностику, без ненаблюдаемых
  отклонений promise. Существующее синхронное поведение сохраняется.
  Изменять виджет из его render/status callbacks по-прежнему запрещено;
  читать статус разрешается.

## Приёмочные сценарии будущей реализации

Управляемые promise, итераторы со счётчиками и детерминированный планировщик:

1. Отложенное первое значение, пустой источник, throw/reject фабрики/получения
   итератора/next, конечный и бесконечный потоки, игнорирование return-значения,
   дополнительный запрос EOF.
2. Один запрос одновременно; объединение повторных команд; отсутствие чтения
   вперёд/опроса; разница Play и ручного Next при получении результата; сброс
   остатка времени при ожидании и продолжение с прогресса ноль.
3. Pause/Previous до и после результата; ограничение готового слота, вытеснение
   окна, EOF/финальная пауза, скорость, скрытие документа и учёт бюджета за кадр.
4. Ошибка кандидата Restart и откат, результат/ошибка старого запроса во время
   подготовки, ожидание успешной/неуспешной очистки, повторный Restart, ошибка
   старого return и незавершающийся старый запрос. Не больше двух итераторов,
   включая повторные попытки.
5. Dispose при первом чтении, Play, подготовке кандидата и очистке старого;
   повторный dispose, реакция/отсутствие реакции на отмену, последовательный
   return, обработка поздних отклонений, некорректные/нетерминальные результаты
   итератора и отсутствие callbacks после dispose.
6. Приоритет ошибок операции/очистки/уведомления и запрет синхронного reentry;
   headless-потребители только с ES2022, прежние sync-тесты и изоляция пакета.

Отдельный [адаптер и результаты локальных проверок](async-source-api.md) теперь
реализованы/описаны: прошли 19 тестов адаптера, все 244 теста репозитория,
потребители установленного архива и изоляция bundles на headless-этапе.
Интеграция с виджетом теперь тоже реализована: [API и результаты](player-async-api.md)
фиксируют 265 успешных тестов, проверку архива и 13 нативных браузерных проверок.
