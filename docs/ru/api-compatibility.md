# Политика совместимости публичного API

[English](../api-compatibility.md) · [Стабилизация](../api-stability.md) · [Ревизия API](../api-readiness-0.16.0.md) · [Проверенные окружения](../support-matrix.md)

**Актуальный объём, 2026-11-17.** Выпущенная 1.1.0 содержит десять entry. U3
одинаково защищает публичные типы, ошибки, окружения и поведение восьми прежних
модулей и /graph + /canvas/graph. Экспериментальных entry нет. Прежним восьми
импортам не нужна миграция с 1.0.0. [Отчёт выпуска](../releases/1.1.0.json).

Датированные ревизии/кандидаты сохраняют прежний объём. [Текущий индекс](current-api.md)
отделяет выпущенное от неопубликованных локальных /tree и /canvas/tree. При первом
выпуске они получат ту же защиту; npm 1.1.0 не содержит ни одного из них.
[Ревизия к 1.2.0](tree-readiness-1.2.md) выбирает совместимый minor.
T1 исправлен с сохранением контракта безопасных границ; релизные шаги ещё открыты.

## Публичная поверхность

Импортируемые пути определяет только export map. Выпущенная 1.1.0: **10 entry,
24 runtime-имени, 95 type-only экспортов, 83 различных типа**. База 1.0.0 имела
8 / 21 / 69 / 57. Общие Worker-типы считаются по обоим путям; классы — runtime-имена.
[Инвентарь](current-api.md) и [ревизия 1.1](graph-readiness-1.1.md).

| Суффикс entry | Runtime-имена | Type-only имён |
| --- | --- | --- |
| `/playback` | `createPlayer`, `createStatePlayer`, `createTimeline`, `createStepEmitter`, `createRewindBuffer`, `createAsyncSource` | 10 |
| `/scene` | `createSceneFrame`, `createSceneRenderer`, `createSceneProjector` | 5 |
| `/array` | `createArrayTrace`, `defineArrayAlgorithm`, `createArrayPlayer`, `createArrayTimeline` | 11 |
| `/canvas` | `arrayScene`, `createArrayRenderer`, `createSortRenderer` | 4 |
| `/canvas/viewport` | `createCanvasViewport` | 3 |
| `/player` | `Player` | 4 |
| `/worker` | `createWorkerSourceFactory`, `WorkerSourceError` | 17 |
| `/worker/runtime` | `exposeWorkerSource` | 15 |
| `/graph` | `createGraphTrace`, `graphScene` | 22 |
| `/canvas/graph` | `createGraphRenderer` | 4 |

Защищены экспортируемые имена, сигнатуры, generics/вывод типов, выбор overload
для прежних вызовов, readonly/optional-поля и достижимые публичные структурные
типы, даже если определены в приватном файле. Защищены документированные defaults,
области входов, смысл состояний/событий/результатов, индексы, правила ссылок и
immutable-данных, время/порядок callbacks, ленивость, владение, отмена, завершение,
приоритет ошибок и семантика dispose/closed.

Примеры: первый синхронный headless render и ленивый Start виджета, EOF без
lookahead, вытеснение окна перемотки, повторный вход U1, проверка скорости U2
до lifecycle, лимит работы RAF и долг времени, async ready slot и барьеры очистки,
копирование/transfer буферов и запрет общей памяти. Тождество
`createSortRenderer === createArrayRenderer` защищено. Документированные keyboard/
accessibility-правила, ключи labels и CSS custom properties — публичные точки
интеграции; переписывание UI не может молча их нарушить.

Сейчас нет root/CommonJS entry и публичных `/core`, `/compat`, deep imports
`src/*`/`dist/*`. Наличие внутренних файлов в архиве не делает их публичными.
Worker-конверты, channel/version-константы и сырые сообщения приватны: это не
прикладной протокол и не формат сохранённых данных. Host и endpoint используют
одну версию пакета; сочетания разных версий не входят в выбранную гарантию.
Приватный протокол может меняться совместимо, если matched host/endpoint
сохраняют публичное поведение. Согласованное развёртывание и cache invalidation
модуля Worker принадлежат приложению.

Внутренние алгоритмы, кэши, helpers, вложенность DOM, недокументированные classes/
data attributes, имена файлов/чанков и размеры байтов не являются стабильным API.
То же относится к числу callbacks без явного обещания, случайному тождеству
wrapper-объектов, точным пикселям/шрифтам, текстам UI, FPS, времени GC и benchmark.
Это не разрешает менять документированные timing, владение, приоритет цветов,
границы ресурсов и доступный смысл управления. Алгоритмы приложения, примеры,
сайт, видеопроцесс и приватные test helpers не входят в API пакета.

## Типы и расширяемость

Для новых graph entry после выпуска закрыты GraphEvent.type, ключи GraphObjects
и режимы nodeCaptions auto/hidden; роли остаются открытыми строками. Изменение
обязательных структурных членов и расширение закрытых вариантов требуют
прежней проверки breaking-совместимости.


Публичные discriminants и literal unions считаются **закрытыми**, если конкретный
будущий API заранее явно не объявит открытую границу расширения. Это включает
`ArrayEvent.type`, phase/mode/preparing Player, async read/close kind, Worker
error code/origin/phase, cancellation и termination kind. Новый вариант ломает
exhaustive switch даже при opt-in выдаче в runtime и требует breaking-релиза.
Отдельный новый тип/метод при прежних областях возврата старого API может быть
совместимым дополнением. Прикладные generic events и документированный реестр
custom scene сохраняют свои существующие точки расширения.

Новое обязательное публичное поле, метод или член callback — breaking, в том
числе в output/report interface: потребитель может создавать fixtures,
реализовывать интерфейс и использовать structural assignment. Optional → required,
потеря readonly-гарантий, сужение параметра, расширение области результата,
изменение inference и различий undefined/null также требуют проверки и breaking-
релиза, если меняют прежнее поддерживаемое использование.

Новые optional-опции/поля, необязательные последние параметры, overloads и
экспорты допустимы в minor только при совместимости прежних вызовов, реализаций,
inference и defaults. Точный набор ключей объекта, exhaustive `keyof`-карты и
произвольные дополнительные свойства приложения не являются гарантией расширения:
optional-добавление может добавить ключ. Поведение неизвестных опций гарантируется
только там, где определено конкретным контрактом. Это не разрешает перекрывать
прежние поля или ослаблять описанный входной контракт. Само по себе «новое поле»
или «расширенный тип» не доказывает совместимость.

## Ошибки входят в контракт

| Поверхность | Что защищено |
| --- | --- |
| Валидация/отказ команды библиотеки | Описанный класс и условия, синхронный throw или promise rejection, порядок argument/lifecycle-проверок и эффекты до отказа |
| Исключения приложения/источника | Описанное сохранение исходного unknown, включая non-Error/undefined, приоритет primary/cleanup, передача напрямую, callback или report |
| Async отмена/закрытие | Read/close discriminants, быстрая логическая отмена и отложенная физическая очистка, never-rejecting report promise там, где обещан, смысл и границы диагностик |
| Нормализованные ошибки Worker | Публичный класс WorkerSourceError, readonly metadata, закрытые code/phase/origin, семантика descriptor и cleanup report |

Стабилизируются только явно описанные классы: наблюдение в реализации или
случайном тесте само по себе не создаёт обещание. Если обещан только общий Error,
потребитель не может рассчитывать на конкретный подкласс. Ревизия 1.0 должна
описать каждый предполагаемый класс/способ доставки или указать предел гарантии.
Это не глобальное правило TypeError для всех неверных типов и RangeError для
всех чисел: U2 намеренно использует RangeError для любой неверной скорости,
включая неверные runtime-типы, до lifecycle-проверок.

Текст сообщения, stack, сведения о месте вызова и browser-native wording/codes
не фиксируются как идентификаторы ошибок библиотеки. Для машинной обработки
служат структурные поля/discriminants. Значения приложения остаются его данными
по правилам identity/clone/truncation; descriptor не обещает восстановление
прототипа/тождественности удалённого Error.

Смена установленного класса, границы normalized/original, победителя primary,
способа throw/reject/report или порядка валидации для поддерживаемого вызова —
breaking. Исправление приёма уже запрещённого контрактом входа допустимо в patch
с описанием последствий. Неоднозначность сначала явно разрешается, а не молча
объявляется дефектом реализации. Последующее решение **U5 сохраняет identity**
host postMessage throw как unknown с host/post-контекстом отчёта. Cancel failure —
исходная cleanup issue внутри прежней сводки; [контракт U5](worker-post-errors.md)
определяет границу и приоритет. [75 постоянных публичных/installed регрессий](../checks/u5-post-errors-regressions-2026-11-14.json)
прошли перед 1.0 и входят в выпущенную базу. Отчёт выпуска 1.1 фиксирует
последующую приёмку точного кандидата.
Сама политика U3 не вводила runtime-изменений.

## Окружения и загрузка

Безопасность импорта, lib деклараций, runtime-возможности и проверка конкретных
версий — разные гарантии. Все десять выпущенных runtime-entry сохраняют импорт без
DOM/Worker globals и без выделения внешних ресурсов при импорте; это не делает
их активные browser-операции доступными в Node.

| Entry | Lib деклараций | Активный runtime |
| --- | --- | --- |
| `/playback`, `/scene`, `/array`, `/graph` | ES2022, без обязательных DOM/ambient Node types | Headless JS/iterables; async-адаптер с собственным DOM-free cooperative signal |
| `/canvas` | ES2022 + DOM | Canvas 2D host, bitmap-координаты, без неявного владения viewport |
| `/canvas/graph` | ES2022 + DOM | Canvas 2D host; явный logical size, bitmap/CSS-размеры принадлежат приложению |
| `/canvas/viewport`, `/player` | ES2022 + DOM | Browser DOM/window и описанные measurement/scheduling API, явные создание/монтаж |
| `/worker` | ES2022 + DOM; browser-Worker host с WebWorker types также описан | Dedicated module Worker host, native clone/transfer, ленивое эксклюзивное владение |
| `/worker/runtime` | ES2022 + WebWorker, отдельно от DOM | Явная установка dedicated Worker endpoint и совместимая source factory |

Начальные цели проверки 1.0 сохраняют прежнюю границу: Node 22.x/24.x/26.x на
Windows/Linux для headless/импорта/потребителей; TypeScript
5.0.4/5.4.5/5.9.3/6.0.3 со строгими NodeNext/Bundler, ES2022 и соответствующими
раздельными DOM/WebWorker lib. Это выбранные конфигурации, а не любой промежуточный/
будущий компилятор и не каждый исторический Node patch. Реальный кандидат должен
зафиксировать точные версии и runner-конфигурации. Нового engines-ограничения
или изменения зависимостей это решение не вводит.

Потребители проверяются с `strict`, `exactOptionalPropertyTypes`,
`noUncheckedIndexedAccess`, `skipLibCheck: false` и явными lib; headless fixtures
не требуют ambient Node types. DOM и WebWorker проверяются отдельными программами,
без объединения в одну разрешающую среду.

Browser-проверки ограничены записанным Windows-хостом встроенного Chromium и
сценариями [матрицы поддержки](../support-matrix.md#current-support-boundary).
Его UA не задаёт minimum Chromium или гарантию desktop Chrome/Edge. Точечные
desktop-проверки viewport не сертифицируют весь API восьми entry. Firefox,
Safari/iOS, другие WebViews, CommonJS, Bun/Deno, Node worker_threads, SharedWorker
и ServiceWorker остаются вне обещания. Для расширения нужны выбранные цели и
доказательства; отсутствие проверки не доказывает несовместимость. Import maps
нужны standalone-примерам, а не любому bundled-применению библиотеки.

Графы существующих entry сохраняют разделение: headless-потребители не получают
DOM types и обязательные UI/Worker imports; `/canvas/viewport` независим;
Worker-модули не загружаются неявно прежними шестью entry. Runtime dependency
и polyfill не становятся обязательными для этих восьми entry. Совместимая
оптимизация может менять чанки/байты, но не требования загрузки/host.
Исключение выбранной цели или повышение требований language/lib/host — breaking,
даже если upstream изменил поддержку. Смена build tool сама по себе внутренняя,
если сохраняются output, декларации и граница потребителей.

## Допустимые изменения релиза

Классификация идёт относительно последнего опубликованного контракта и
поддерживаемого использования, одновременно для runtime, типов, ошибок и
окружений. При пересечении строк действует более строгое правило. Само
объявление deprecation не разрешает удаление.

| Изменение | В 0.x | В 1.x |
| --- | --- | --- |
| Исправление docs/test/tooling или внутренняя оптимизация с сохранением контракта; исправление уже запрещённого входа | Patch | Patch |
| Совместимый entry/export, optional-возможность/поле или проверенное новое окружение | Minor; только новые доказательства проверки допустимы в patch | Minor; только новые доказательства проверки допустимы в patch |
| Вариант закрытого union, обязательный structural member, удаление/переименование, несовместимые тип/default/lifecycle/error/host | Явный breaking minor | Следующий major |
| Переход с 0.x на проверенный стабильный baseline | Отдельно согласованный и проверенный кандидат 1.0 | Не автоматическое следствие успешного patch |

Patch в 0.x не вводит намеренных breaking-изменений контракта. Minor в 0.x может
их вводить с заметным breaking-change описанием, затронутыми entry, примером
до/после и миграцией. В 1.x несовместимое изменение ждёт major; предпочтительны
совместимая альтернатива и deprecation хотя бы за один minor, когда это возможно.
Фиксированного срока уведомления, LTS/backport-графика и частоты релизов нет.
Security/isolation-исправление может остановить уже запрещённое использование,
но не является общим разрешением сломать поддерживаемый контракт в patch:
последствия описываются и выбирается соответствующая граница релиза.

Ранее не определённую деталь можно совместимо уточнить, с явными release notes
при наблюдаемом эффекте. Противоречивые документы требуют решения и проверки
влияния, а не автоматического выбора patch. Здесь не выбирается версия и не
разрешается выпуск накопленных F1/U1/U2.

## Проверка кандидата и оставшаяся работа

Для изменения определить затронутые entry, успешные/ошибочные пути, типы и
окружения, классифицировать изменение и записать миграцию при необходимости.
Проверить установленный архив, точные экспорты/закрытые пути, inference и negative
type cases, затронутые lifecycle/error-регрессии и границы сборки. Использовать
выбранную Node/TS CI-матрицу и точечные native browser/Worker-проверки реального
кандидата по затронутому поведению. Старые local/mock/native результаты сохраняют
свой объём; зелёные проверки не расширяют набор поддерживаемых целей.

U4 согласовал восемь прежних справочников; в 1.1 добавлены два графовых под
той же политикой. Выпуски 1.0 и 1.1 завершены; см. [отчёт 1.1](../releases/1.1.0.json).
Для будущих изменений приёмка кандидата и публикация остаются отдельными
действиями по поручению владельца. [Проверка U3](../checks/u3-compatibility-policy-2026-11-14.json)
фиксирует инвентарь и отсутствие изменений реализации на этом docs-этапе.
