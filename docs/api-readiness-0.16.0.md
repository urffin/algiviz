# Ревизия публичного API перед 1.0 — версия 0.16.0

**Исторический аудит 0.16.0.** Актуальная [итоговая ревизия](ru/api-readiness-1.0.md)
([English](api-readiness-1.0.md)) закрывает F1/U1–U5 в их границах, но фиксирует
новый блокер F2. Исходные таблица/JSON ниже сохраняются как исторические результаты.

Проверено 2026-11-14. Опубликованный baseline: `15f204195908f02e561fda50d1ba25dc4dab5b29`;
рабочая копия до ревизии: `12173e01b9e175f18ea63c6becf41eb7724a9c56`.
Сверены package exports, исходники, декларации, контракты, потребители и результаты
релиза. Добавлены диагностические воспроизведения. API, production-код, версия,
зависимости и опубликованный пакет этой ревизией не меняются.

**Вывод исходной ревизии выпущенной 0.16.0: библиотека требует изменения перед 1.0.**
Найден один подтверждённый дефект изоляции Worker: F1, затрагивающий обе
Worker-точки входа. Поверхность ошибок host postMessage содержит неоднозначность
между документами и вынесена в уточнение U5.
Из восьми точек входа три готовы по проверенному контракту, три требуют
уточнения и две требуют изменения реализации. Уточнения U1/U2/U5 сами по себе
не доказывают необходимость менять сигнатуры или поведение. Решение о выпуске
1.0 остаётся отдельным решением владельца.

## Последующее исправление F1 — локально, 2026-11-14

Владелец отдельно разрешил исправить F1 с регрессиями, без изменения публичного
API и публикации. Общий inspectData теперь читает внутренний backing buffer
WebAssembly.Memory через сохранённый native getter и проверяет ArrayBuffer
brand. Shared backing storage отклоняется даже без глобального конструктора
SharedArrayBuffer. Проверка не зависит от instanceof или Symbol.toStringTag и
не вызывает пользовательский buffer getter.

Изменён только приватный валидатор данных. Публичные сигнатуры, экспорты, коды
ошибок и lifecycle сохранены. Декларации сравнены с сохранёнными перед правкой;
различий после нормализации CRLF/LF нет. Версия остаётся 0.16.0, исправление
не опубликовано. U1–U5 этой задачей не разрешаются и не меняются.

Прошли 312 тестов, включая восемь новых: пять через публичный Worker API и три
проверки границ самого wire validator. Они покрывают input/state, вложенные
циклические Map/Set/Error cause, чужой realm, подмену сообщений обеими сторонами,
читаемость ранее переданного буфера, отсутствие повторных запросов и очистку.
Семь из восьми новых тестов сначала падали на прежней сборке; оставшийся —
контроль против ложного распознавания обычного объекта. Свежий установленный
архив прошёл 32 Worker-сценария и потребителей TypeScript 6.0.3 NodeNext/Bundler
с раздельными headless/DOM/WebWorker окружениями. Изоляция сборок также прошла.
[Итоговая проверка исправления](checks/worker-memory-fix-2026-11-14.json) содержит
сводку тестов, сравнение 34 поставляемых деклараций и SHA-256 изменённых файлов.

Нативный [отчёт исправления](checks/worker-memory-fix-browser-2026-11-14.json)
подтверждает 6/6 сценариев: direct/nested input и state отвергаются с
WorkerSourceError serialization/serialize, обычные copy/transfer сохраняются.
Все Worker завершились с acknowledged/requested, неожиданных ошибок и
оставшихся Worker — ноль. Исторические отчёты ревизии выше сохраняют старый
baseline и не выдаются за проверку исправленной сборки.

После исправления F1 у /worker остаётся уточнение U5; собственная граница
/worker/runtime больше не имеет найденного обязательного изменения реализации.
Это закрытие конкретного дефекта в рабочем дереве, не автоматическое одобрение 1.0.

Повторить текущую нативную проверку: node scripts/serve-api-review.mjs --verify.
Страница с verify=1 сохраняет новый отчёт отдельно от исходного воспроизведения.
Исторический scripts/review-api-0.16.0.mjs намеренно требует неизменённого
опубликованного baseline; запускать его поверх исправления для новой зелёной
проверки нельзя.

## Требует изменения

### F1. Общая память скрывается внутри WebAssembly.Memory

Приоритет: блокирующее расхождение перед 1.0. Затронуты `/worker` и
`/worker/runtime`; приложение Player, использующее такую фабрику, наследует дефект.

Контракт [запрещает общую изменяемую память](worker-source.md#serialization-and-snapshot-ownership),
в том числе вложенные SharedArrayBuffer/views. Однако
[inspectData](../src/worker/data.ts) проверяет собственные свойства объектов,
Map/Set и буферы/views. Внутреннее хранилище `WebAssembly.Memory` не попадает в
этот обход. Native structuredClone в проверенных хостах принимает shared Memory.

| Направление | Ожидается | Фактически |
| --- | --- | --- |
| Init приложения → Worker | Общая память отклонена до принятия input | Worker принимает Memory; запись приложения меняет значение, читаемое Worker: `7 → 42`. |
| State Worker → приложение | Общая память отклонена; переданный снимок не связан с дальнейшими записями Worker | Worker принимает/отправляет Memory; прежний host-снимок меняется `7 → 42` без нового запроса состояния. |

Оба направления подтверждены через публичные фабрики на управляемом транспорте
с настоящим structuredClone, затем **на настоящих dedicated module Worker во
встроенном браузере**. В нативной проверке использована cross-origin isolation;
это условие воспроизведения общей памяти, а не новое требование адаптера.
Оба Worker завершились с acknowledged/requested, оставшихся Worker и неожиданных
ошибок — ноль. [Нативный отчёт](checks/api-review-worker-native-2026-11-14.json)
содержит наблюдения и 15 SHA-256 исходников, сборки и HTML-стенда.

Контрольный сценарий с обычным `SharedArrayBuffer` в объекте по-прежнему
отклоняется с `code: 'serialization'`: дефект относится к скрытому внутреннему
содержимому объекта, а не к отсутствию запрета вообще. Это нарушение изоляции
данных/снимков, а не установленная возможность исполнения чужого кода.

Направление следующего исправления: обеспечить запрет shared Memory в обоих
направлениях и проверить границы допустимого графа с непрозрачными native
объектами. Простого запрета экземпляров через `instanceof` может быть недостаточно
для разных realm. Регрессии должны покрыть input/state, вложенные контейнеры,
старые retained snapshots и обычные copy/transfer сценарии. Исправление не
обязательно требует менять публичные сигнатуры. В исходной ревизии оно не
реализовывалось; последующее локальное исправление и регрессии описаны выше.

Нормативная переносимость клонирования Memory здесь не предполагается. Она
обсуждается в [upstream issue WebAssembly/spec #2155](https://github.com/WebAssembly/spec/issues/2155).
Основание находки — измеренное поведение поддерживаемого браузерного хоста и
собственный контракт AlgiViz, а не обещание одинакового поведения всех движков.

## Требует уточнения

### U1. Повторное управление headless-плеером из callbacks

`/player` и `createRewindBuffer` явно отвергают повторные команды из callback.
Headless `createPlayer`/`createStatePlayer` не имеют такой защиты и не описывают
политику. Это также касается `createArrayPlayer`, использующего тот же движок.

Проверка: render состояния `1` вызывает вложенный `nextStep()`. Внешний вызов
возвращает кадр `1`, `player.frame.current` уже равен `2`; отрисовки идут `[0,1,2]`.
Это наблюдение не объявляется нарушением: приложение явно вызвало две команды,
а запрет или гарантия вложенного управления пока не установлены.

**Контракт выбран 2026-11-14:** [полное решение U1](ru/headless-reentrancy.md)
([English](headless-reentrancy.md)). Повторные nextStep, advance (включая ноль)
и первый dispose на активном экземпляре синхронно отклоняются обычным Error.
Чтение frame/finished и команды другого свободного экземпляра разрешены.
Повторный dispose после логического disposal — no-op, в том числе из cleanup.
Пойманный отказ не портит внешнюю операцию; непойманный следует её обычному
failure/cleanup пути с сохранением первичной ошибки. Штатный terminal return
отличается от уже начатого disposal. Охвачены source/result/step getters,
вложенные чтения, синхронные helpers и граница отложенных команд.

**Последующая реализация, 2026-11-14:** U1 выполнен локально, без публикации.
Общий движок защищает команды и чтение frame с прикладными getters, а адаптер
plain states отдаёт очистку движку после фиксации disposal. Сохраняются
идемпотентность, первичная ошибка и независимость экземпляров. 61 публичная
регрессия покрывает матрицу контракта; весь набор содержит 373 успешных теста.
Публичные сигнатуры/экспорты/версия сохранены; изменена только приватная декларация
state-steps. Итоговые installed-package и прочие проверки — в
[отчёте U1](checks/u1-reentrancy-2026-11-14.json). Исходный срез 0.16.0 в таблице
выше остаётся историческим, а U2–U5 требуют отдельных решений.

### U2. Классы ошибок числовой валидации Player

`setSpeed(0)`, отрицательное значение, NaN и Infinity во всех режимах отклоняются
до изменения состояния. Но sync source/history дают RangeError, asyncSource —
TypeError. Скорость остаётся `1`, фаза idle, фабрики не вызываются.
Основания: [sync controller](../src/player/controller.ts) и
[async controller](../src/player/async-controller.ts), 12 наблюдений в JSON.

Нынешний контракт обещает отклонение неверной скорости, но не закрепляет класс
исключения этого метода. Поэтому это уточнение, не уже доказанное нарушение
контракта. До 1.0 надо решить, являются ли классы ошибок числовой валидации
стабильными, и либо унифицировать их, либо прямо документировать границу.
Текст сообщений и оригинальные исключения браузера по-прежнему не должны
автоматически становиться обещанием библиотеки.

**Контракт выбран 2026-11-14, без реализации и публикации:**
[решение U2](ru/player-speed-validation.md) ([English](player-speed-validation.md)).
Для source/history/asyncSource/Worker принимается только конечный примитивный
number > 0; любое неверное значение даёт встроенный RangeError без приведения.
Проверка значения предшествует disposed/reentrancy; отказ не меняет состояние
и не вызывает callbacks. Допустимая скорость сохраняет намерения/запросы и долг
playback-времени, сбрасывает baseline, доступна при подготовке/ожидании/очистке
и не восстанавливает failed/finished-сеанс. Полный документ задаёт граничные
значения, исключения из callbacks и матрицу будущей реализации.
На этапе выбора контракта async/Worker TypeError сохранялся в коде; read-only
baseline без изменения реализации зафиксирован в
[отчёте проектирования](checks/u2-speed-contract-2026-11-14.json).
Таблица исходной ревизии выше остаётся историческим срезом 0.16.0.

**Последующая реализация, 2026-11-14:** async-контроллер теперь выдаёт RangeError,
совпадая с sync/history; U2 выполнен локально, без публикации. Прошли все 428
тестов, включая 55 новых публичных регрессий и те же 55 на установленном архиве,
а также строгие NodeNext/Bundler-потребители. Проверены классы/приоритет ошибок,
отсутствие эффектов при отказе, lifecycle, callbacks, baseline/долг времени.
Worker-случаи используют настоящий адаптер/endpoint с внутрипроцессным
клонирующим транспортом; новая нативная проверка здесь не заявляется.
Публичные декларации/экспорты, версия и зависимости сохраняются.
Результаты — в [отчёте реализации](checks/u2-speed-implementation-2026-11-14.json).

### U3. Единая политика совместимости всех восьми entry

Старый план просит решение о долгосрочной поддержке четырёх исходных модулей,
но публикуется уже восемь. Нужен явный перечень того, что стабилизируется в 1.0:
точки входа, типы, поля, defaults, lifecycle, ошибки и поддерживаемые окружения.
Необязательность модуля для загрузки сама по себе не делает его API нестабильным.

Отдельно закрепить подход к расширению discriminated unions: новый `ArrayEvent`,
phase/status/result kind или Worker error code может сломать exhaustive switch
потребителя. Новое обязательное поле публичного структурного типа может сломать
его собственные fixtures/объекты. Такие изменения требуют явного решения о
совместимости; автоматически считать их безопасными добавлениями нельзя.
Это предложение политики, не выбранное этой ревизией новое правило semver.

**Политика выбрана последующим шагом 2026-11-14, без реализации и публикации:**
[полный U3](ru/api-compatibility.md) ([English](api-compatibility.md)). Все восемь
entry получают одинаковые гарантии в 1.x, включая optional Player/Worker.
Защищены публичные пути/имена/типы, defaults, lifecycle, описанные ошибки и
окружения. Закрытый discriminant union и обязательный structural member нельзя
расширять в совместимом релизе. Optional-дополнения требуют сохранения прежних
вызовов/inference/семантики; точный набор ключей не замораживается.
Patch сохраняет контракт, совместимая возможность идёт в minor; breaking в 0.x
идёт в явно описанный minor, в 1.x — в следующий major. Приоритет ошибок,
способ доставки и выбранная граница окружений входят в классификацию.

U3 закрыт как решение политики; это не готовность к 1.0. U5 о postMessage
не решён этим правилом, U4 требует отдельного согласования документации.
Историческая таблица выше и прежние доказательства не переписываются.
Read-only инвентарь/границы и отсутствие изменений реализации записаны в
[отчёте U3](checks/u3-compatibility-policy-2026-11-14.json).

### U5. Идентичность или нормализация исключений host postMessage

Исходная неоднозначность аудита 0.16.0 описана ниже; последующее решение U5
зафиксировано в конце этого раздела.

Контракт поведения говорит, что [локальные исключения сохраняют идентичность](worker-source.md#errors-and-observable-failure).
[Error surface](worker-source-api.md#error-surface-and-bounded-diagnostics)
отдельно упоминает сохранение ошибок прикладных фабрик и перечисляет channel-post
failure как случай transport code. Не определено, должен ли сам host postMessage,
бросивший native exception, попасть под общее сохранение локальных ошибок либо
под нормализацию в WorkerSourceError. Поэтому объявлять реализацию однозначно
ошибочной пока нельзя.

Текущее поведение [host transport](../src/worker/index.ts) воспроизведено для
init и pull. При fault injection postMessage бросает DOMException с
name InvalidStateError. Публичный next отклоняется тем же объектом:
instanceof WorkerSourceError false, code 11. Transport closed при этом сообщает
kind failed, origin host, phase post, Worker завершается один раз.
Это управляемая инъекция, не воспроизведение реального отказа браузерного канала.
Обычное исключение прикладной Worker-фабрики также сохраняет идентичность.

До 1.0 выбрать и одинаково описать одну границу: сохранять native host throws
с контекстом в session.closed или нормализовать channel failure с origin/phase.
Если выбрана нормализация, потребуется отдельное изменение поведения и регрессии
обоих post-путей с сохранением прежних правил для прикладных фабрик. Если выбрано
нынешнее поведение, достаточно явно устранить двусмысленность таблицы кодов.
Это решение не следует принимать автоматически как исправление дефекта F1.

**U5 уточнён последующим шагом 2026-11-14, без реализации и публикации:**
[выбранный контракт](ru/worker-post-errors.md) ([English](worker-post-errors.md))
сохраняет исходный host postMessage throw как unknown. Активный init/pull failure
даёт ту же primary в чтении и failed-отчёте с origin host, phase post; cancel throw
записывается как реальная cleanup issue, не подменяя выбранную failure/disposal.
Прежний WorkerSourceError с code cleanup остаётся сводкой очистки и хранит
исходное значение внутри первой issue, а не нормализует первичную send-ошибку.
Правила transport versus outer AsyncSource closed, прямого return, lateReadError,
undefined и порядка наблюдения определены в контракте. Таблица кодов Worker
согласована с этой границей; instanceof WorkerSourceError не охватывает все отказы.

30 read-only fault-injection проб текущего публичного адаптера подтвердили эти
ветви без изменения кода. [Отчёт U5](checks/u5-post-errors-contract-2026-11-14.json)
отделяет пробы от постоянных регрессий, full-suite/installed/native/CI-проверки.
U5 закрыт как решение контракта; отдельный следующий шаг — постоянные регрессии
и проверка baseline/кандидата, а не обязательная нормализация или новый API.

**Последующее закрепление регрессиями, 2026-11-14:** прошли 75 постоянных публичных
U5-тестов и те же 75 на свежем установленном архиве; весь набор — 503 теста.
Строгие NodeNext/Bundler-потребители прошли. Проверены init/pull/cancel, unknown/
falsy/hostile значения, create/post getters, first/late/cleanup priority,
повторное закрытие, ACK/forced shutdown, copy/transfer и Player lifecycle.
Production-правки не потребовались; runtime/декларации и публичные экспорты прежние.
Новой native/CI/registry-проверки нет, публикации нет.
[Отчёт регрессий](checks/u5-post-errors-regressions-2026-11-14.json) отделён от
прежнего design/probe-отчёта; до решения о релизе остаётся review baseline/кандидата.

## Что уже готово и какие ограничения сохраняются

- Для sync step/state playback различие terminal predicate и дополнительного
  EOF-запроса намеренно. Timeline хранит явную историю; rewind — ограниченное
  окно. Эти модели не нужно объединять ради одинаковых названий методов.
- Шаги/state/event generic playback не deep-clone/deep-freeze. Array trace
  создаёт frozen снимки и сохраняет ID; `done` не доказывает сортировку.
- Scene callbacks — отрисовка кадра, не гарантированные lifecycle hooks.
  Кэш требует immutable endpoints и pure projection. Layout принадлежит приложению.
- Canvas renderer работает в bitmap-координатах; viewport — в CSS content
  coordinates. Их разница документирована и не является находкой этой ревизии.
- Async dispose логически мгновенный, closed ждёт физическую очистку. Обычный
  async source, игнорирующий отмену, может ждать бесконечно; Worker имеет отдельный
  конечный grace/terminate и отдельный отчёт. Три closed-отчёта не взаимозаменяемы.
- Node worker_threads, SharedWorker/ServiceWorker, общая память, worker pools,
  browser-wide поддержка и автоматическое развёртывание Worker не обещаны.
  Выбранные TypeScript/Node конфигурации и встроенный браузер не сертифицируют
  каждую промежуточную версию и каждый бренд браузера.

## Доказательства и воспроизведение

Переиспользованы результаты неизменённого [релизного baseline](releases/0.16.0.json):
304 теста, 11 точных CI jobs, TypeScript 5.0.4/5.4.5/5.9.3/6.0.3 в
NodeNext/Bundler, раздельные ES2022-only/DOM/WebWorker потребители, package/bundle
checks, свежая registry-установка и 20+25 нативных сценариев предыдущего этапа.
Полный старый набор заново не запускался. Его успех не отменяет новых находок:
shared WebAssembly.Memory и инъекция host-post failure в него не входили.

В этой ревизии выполнены: инвентаризация деклараций, фактический импорт всех
восьми runtime namespace без глобальных DOM/Worker, проверки alias/private paths,
контроли обычного SAB и исходных factory errors, две shared-Memory пробы,
два инъецированных post-failure сценария, headless reentrancy и 12 speed-проб.
Символьная инвентаризация с skipLibCheck не выдаётся за новый compiler matrix.
JSON содержит версии окружения и SHA-256 кода/сборки/диагностики.

```sh
# Использовать неизменённую сборку 0.16.0; если dist отсутствует — npm run build.
node scripts/review-api-0.16.0.mjs
node scripts/serve-api-review.mjs
```

Первая команда печатает [диагностический JSON](checks/api-readiness-0.16.0.json).
Её exit code 0 означает завершение ревизии, а не готовность к 1.0.
Вторая выводит localhost URL; во встроенном браузере кнопка запускает два
нативных сценария и сохраняет [отчёт](checks/api-review-worker-native-2026-11-14.json).
Страница намеренно показывает обнаруженные нарушения, а не зелёный acceptance.

Первый шаг исходной ревизии, исправление F1 с регрессиями, теперь выполнен локально.
Контракты U1 и U2 выбраны и реализованы/проверены локально, без публикации.
Политика U3 выбрана, документация U4 согласована, контракт U5 определён.
U5 закреплён постоянными регрессиями локально. Последующая
[итоговая ревизия](ru/api-readiness-1.0.md) повторно оценила восемь entry и нашла
