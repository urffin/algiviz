# Аудит минимального примера: обязанности пользователя и упрощения API

Дата: 2026-10-27. Проверенная версия: 0.8.3.
Статус: рекомендации; новые API ниже не реализованы. 1.0 остаётся отложенной.

## Вывод

Минимальный пример одновременно обучает двум независимым возможностям:
воспроизведению состояний и диспетчеризации объектов сцены. Для одной точки без
плавного перехода достаточно `/playback` и обычного состояния `{ x }`.
`/scene` нужен для демонстрации собственных типов, идентичностей и обработчиков,
но не является обязательной оболочкой любого алгоритма.

Большой размер учебной страницы не равен размеру интеграции: скрытый Canvas,
запись вызовов, подсветка, задержки и кнопка запуска нужны объяснению, не библиотеке.
Не стоит переносить эти механизмы в публичный API.

## Что действительно обязан определить пользователь

| Обязанность | Почему нужна | Что уже можно сократить |
| --- | --- | --- |
| Состояния и алгоритм их получения | Библиотека не знает предметную область | Для точки достаточно `{ x }`; проекция не нужна |
| Независимость снимков | Плеер сохраняет ссылки, не клонирует состояния | Создавать новый объект при каждом yield; глубокий freeze не обязателен |
| Формат Step: index/state/event | Текущий контракт `/playback` | `createStepEmitter` снимает ручную нумерацию; событие может быть любым, включая undefined |
| Признак завершения | Текущий player требует isTerminal, ранний конец итератора — ошибка | Одна конвенция событий в приложении; emitter сам завершение не определяет |
| Визуальное представление | Геометрия и backend принадлежат приложению | Рисовать frame.current напрямую без createSceneRenderer |
| Очистка Canvas | Предыдущий кадр иначе остаётся на bitmap | Одна строка в render; библиотека не должна очищать произвольный контекст |
| Продвижение | Плеер не запускает таймеры | Кнопка для учебного примера; rAF только при анимации |
| Жизненный цикл | Создание сразу читает и рисует; перезапуск требует нового источника | Создавать player в обработчике «Начать», dispose при удалении |

Если выбран `/scene`, дополнительно нужны objects, стабильный id, type, data и
обработчик типа. Это полезный контракт для нескольких объектов, связей и
появления/исчезновения, а не только синтаксическая нагрузка.

Canvas beginPath/arc/fillStyle/fill — код Canvas, не дополнительное требование AlgiViz.
Два импорта не повод вводить корневой экспорт или объединять независимые модули.

## Упрощение уже на текущем API

Ниже тот же сценарий без сцены. Требуются Canvas 600 × 160 и кнопка #next;
импорты разрешаются сборщиком. Это пример только playback, не замена примера scene.

```js
import { createPlayer } from '@grundyjs/algiviz/playback';
const ctx = document.querySelector('canvas').getContext('2d');
function* steps() {
    for (const [index, x] of [40, 200, 360, 560].entries()) {
        yield { index, state: { x }, event: index === 3 ? 'done' : 'position' };
    }
}
const player = createPlayer(steps(), {
    stepDurationMs: 1000, finalHoldMs: 0,
    isTerminal: step => step.event === 'done',
    render({ current }) {
        ctx.clearRect(0, 0, 600, 160);
        ctx.beginPath();
        ctx.arc(current.x, 80, 18, 0, Math.PI * 2);
        ctx.fillStyle = '#b39bff';
        ctx.fill();
    },
});
document.querySelector('#next').onclick = () => player.advance(1000);
```

Это 20 строк вместо 28 в интерактивной странице; длина сама по себе не критерий
хорошего API. Сняты понятия scene/id/type/dispatcher, а не только пробелы.
При удалении нужно вызвать player.dispose(); повторное создание должно закрыть
старый источник. После завершения интерфейс должен отключить кнопку.

## Приоритет 1: шаг без знания миллисекунд

Предложение для обсуждения: `player.nextStep()` (имя пока не утверждено).

Сейчас: `player.advance(1000)`, где 1000 дублирует stepDurationMs.
В общих примерах уже есть nextDelta(frame), вычисляющая оставшуюся часть перехода.

Предлагаемый контракт:

- На границе шага потребить ровно следующее состояние и завершить переход к нему.
- В середине перехода завершить текущий переход, не потребляя ещё один шаг.
- Начальный кадр уже показан конструктором; первый nextStep ведёт ко второму состоянию.
- Вызвать render один раз и вернуть Frame, как advance.
- После finished не читать источник; поведение повторного render согласовать с advance.
- На terminal с оставшимся finalHoldMs закончить удержание без чтения источника.
- После dispose и при исключениях сохранять текущие правила cleanup/ошибок.

Это добавление к API, не изменение advance. Проверить генератор с побочными эффектами,
частичный progress, одно состояние, terminal/hold, повторное завершение и dispose.
Timeline имеет другую модель: sample не хранит курсор. Не добавлять в него мутирующий
nextStep автоматически ради симметрии.

## Приоритет 2: удобные значения параметров

Кандидат: finalHoldMs по умолчанию 0. Его явное указание повторяется в минимальных
интеграциях и не описывает алгоритм. Нужно проверить декларации и совместимость:
пропущенное значение сейчас отвергается, явные неверные значения должны отвергаться дальше.

stepDurationMs нужен анимации; произвольный default только скрывает решение.
Сначала проверить nextStep на втором примере, затем решать, нужен ли отдельный
дискретный плеер или удобные настройки. Не добавлять оба варианта одновременно.

## Приоритет 3: генератор обычных состояний — отдельное исследование

Желаемый синтаксис `yield { x }` убирает index/event и done, но обычное завершение
итератора сейчас намеренно считается ошибкой. Это не безопасная косметическая правка.

Предпочтителен явный адаптер/отдельный режим, сохраняющий строгий createPlayer.
Нельзя распознавать Step и State по наличию поля state: пользовательское состояние
тоже может содержать state/index/event.

Чтобы знать, что текущий yield последний, нужен lookahead или следующий запрос.
Lookahead раньше выполняет код генератора и побочные эффекты; без него finished
может стать известен только после дополнительного клика. Нужно определить также
пустой источник, return value, ошибки, бесконечный источник и раннее закрытие.
До этих решений новый overload не предлагать к реализации.

## Что не менять ради краткости

- Не встраивать алгоритмы, тип dot, геометрию и автоматическую раскладку.
- Не клонировать пользовательские снимки автоматически.
- Не менять незаметно первый render при createPlayer: это текущий контракт.
- Не запускать rAF автоматически в универсальном плеере.
- Не убирать id/type из сцен: они нужны идентичности и выбору обработчика.
- Не добавлять хелперы для каждой скобки objects/data: экономия мала, новых понятий больше.

## Ограничения текущего учебного примера

Обработчик читает current.data без null-проверки. Это корректно для постоянного
круга, но не для общего scene-handler: при exit current === null даже при progress 1.
Пример с удалением объекта обязан обрабатывать этот случай.

advance(1000) эквивалентен переходу на одно состояние только при старте на границе
и согласованном stepDurationMs. После advance(400) ещё один advance(1000) завершает
переход к 200 и уже входит в переход к 360 с progress 0.4.

## Проверка и следующий эксперимент

Выполнены read-only пробы на текущей сборке: создание читает/рисует ровно один шаг;
обычные состояния работают без scene; три полных advance дают 40/200/360/560;
частичное продвижение пересекает границу при фиксированном delta; раннее истощение
без terminal выбрасывает ошибку; обработчик exit получает current === null.

Следующий эксперимент: 3–4 вершины графа, генератор меняет activeId, независимые
объекты node/edge и обработчики. Сравнить существующий nextDelta с предложенным
nextStep по количеству знаний, необходимых автору. Не реализовывать вторую версию
алгоритма и не менять публичные экспорты до выбора контракта.
