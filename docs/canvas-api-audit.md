# Аудит /canvas перед стабилизацией

Проверено 2026-11-05: опубликованная 0.11.1, исходники на 0bbae18.
Исходный аудит ниже относится к 0.11.1. Статус исправлений описан отдельно.
Документ не разрешает выпуск 1.0.

## Исправления в 0.11.2 (подготовлены 2026-11-05)

- Максимум вычисляется линейным проходом без разворачивания массива в аргументы.
- До рисования проверяется конечный progress в [0, 1]; нулевой bitmap остаётся no-op.
- Внутри save/restore нормализуются composite/filter/shadow наряду с transform/alpha.
- Входной colors разрешает explicit undefined; неверная или отсутствующая theme
  вызывает TypeError при создании renderer. Имена экспортов и палитры сохранены.
- Справочник RU/EN описывает модель входа, arrayScene, smoothstep, цветовые
  приоритеты, DPR/bitmap, clip, ошибки, владение контекстом и отсутствие scheduler.
- test/canvas-contract.test.mjs добавляет десять регрессий: 150000 элементов,
  конечная геометрия, контекст и исключения, progress, нулевой bitmap, тема,
  undefined-палитра, цветовые приоритеты, идентичности, seek/resize и плотные подписи.
- Установленный пакет проверяет colors: undefined с exactOptionalPropertyTypes,
  неверную тему, раннее отклонение progress и рисование корректного кадра.
- npm test: 127 тестов успешно; npm run test:package: успешно. Отдельная native
  Canvas-проверка подтвердила одинаковые пиксели для исходных composite/filter/shadow,
  восстановление настроек и цвета заливки, неизменность bitmap при неверном progress,
  проброс ошибки рисования и сохранение унаследованного clip.

Перед любым следующим разрешённым выпуском требуется CI точного кандидата.
Замеры FPS и отложенные оптимизации
highlight/создания sceneRenderer не входят в эти исправления.

## Решение

Форма API готова к стабилизации: небольшой необязательный backend для числового
массива из `/array`, а не универсальный набор Canvas-примитивов. Переименования,
новые экспорты и расширение модели массива не нужны. Пользовательские объекты и
другие способы отрисовки уже доступны через `/scene`.

До 1.0 стоит убрать воспроизводимое падение на большом корректном массиве,
закрепить границы владения Canvas-контекстом и проверять progress до рисования.
Отдельно стоит согласовать опциональный colors с runtime и дополнить проверки.

## Проверенный публичный контракт

| Часть | Текущее поведение и оценка |
| --- | --- |
| Экспорты | arrayScene, createArrayRenderer и createSortRenderer; два последних — одна функция, а не отдельные реализации |
| Типы | ArrayObjects, ArrayPalette, ArrayPaletteOverrides, ArrayRendererOptions; возвращаемый renderer имеет выводимый readonly-тип с render(ctx, frame): void |
| arrayScene | Создаёт bar-объекты с исходными id и data: item/index/held; пропускает null, помещает held в индекс пустой позиции |
| Владение | Оболочка scene, objects, объекты и data заморожены; Item сохраняется по ссылке, а не клонируется или дополнительно замораживается адаптером |
| Вход renderer | Неизменяемые ArrayFrame одного trace: фиксированная длина, стабильные id и конечные числовые значения |
| Движение | Позиция между слотами интерполируется по smoothstep p²(3−2p); высота определяется модулем значения, подпись сохраняет знак |
| Состояние шага | Событие, счётчики, held и маркеры берутся из current; это метаданные текущего шага, не интерполируемые величины |
| Цвета | Приоритет held → active → sorted → bar; текст и фон имеют отдельные роли; active определяется событием |
| Палитра | light/dark обязательны в типах; шесть строковых ролей, частичные переопределения копируются, undefined-роли сохраняют тему |
| Размеры | Раскладка по ctx.canvas.width/height, transform временно единичный; при нулевой ширине/высоте нет рисования |
| Плотность | Подписи значений и индексов скрываются при ширине ячейки меньше 24 bitmap-пикселей |
| Повторное рисование | Произвольный порядок кадров и resize не требуют сброса; projector сохраняет максимум две проекции endpoint-состояний |
| Жизненный цикл | Нет RAF, таймеров, записи видео, DOM-контролов или dispose; источник и планирование принадлежат приложению |

Возвращаемый объект renderer заморожен. Внутренний cache проекций не является
историей воспроизведения и не отменяет требование неизменяемости входных снимков.
`arrayScene` можно вызвать в Node без document/window, но декларации `/canvas`
требуют DOM-типов из-за CanvasRenderingContext2D. Headless-контракт остальных
трёх entry points от этого не меняется.

## 1. Исправить до стабилизации: Math.max с разворачиванием большого массива

В `src/canvas/index.ts` максимум вычисляется так:

```ts
Math.max(1, ...items.map(({ data }) => Math.abs(data.item.value)))
```

Число элементов становится числом аргументов вызова. В Node 22.17.0 корректный
trace из 150 000 элементов падает с RangeError: Maximum call stack size exceeded.
На 4 000 элементах тот же путь проходит. Конкретный порог зависит от движка и
стека вызовов; это не допустимый публичный лимит размера массива.

Воспроизведение после сборки, через публичные экспорты:

```js
import { createArrayTrace } from '@grundyjs/algiviz/array';
import { createArrayRenderer } from '@grundyjs/algiviz/canvas';

const state = createArrayTrace(Array.from({ length: 150_000 }, () => 1)).start().state;
const ctx = {
    canvas: { width: 800, height: 450 },
    save() {}, restore() {}, setTransform() {}, fillRect() {}, fillText() {}
};
createArrayRenderer({ theme: 'dark' }).render(ctx, {
    previous: state, current: state, event: { type: 'start' }, progress: 1, stepIndex: 0
});
```

Рекомендация: линейный проход с аккумулятором вместо spread, без изменения
геометрии, цветов или экспортов. Добавить регрессию с большим корректным trace
и заглушкой Canvas. Отсутствие этого падения не означает гарантии FPS или
практической читаемости сотен тысяч столбцов; стоимость сцены остаётся O(n) по
памяти и включает сортировку слоёв O(n log n) на кадр.

## 2. Закрепить до 1.0: владение состоянием Canvas

Renderer вызывает save/restore, устанавливает единичный transform и globalAlpha=1.
Настройки вызывающей стороны восстанавливаются, включая исключение внутри
рисования. Однако сохранение состояния не означает независимости изображения
от всех входных настроек контекста.

Проверка реальным Canvas через установленный @napi-rs/canvas показала:

- При исходном globalCompositeOperation='destination-in' пустой bitmap остаётся
  прозрачным вместо полного кадра.
- Исходные filter='opacity(50%)' и shadowBlur/shadowColor меняют пиксели кадра.
- Исходные scale(2, 2) и globalAlpha=0.4 не меняют результат, а после render
  восстанавливаются. Эти свойства renderer уже изолирует намеренно.

Это проверка native Canvas, не утверждение о визуальном тестировании браузеров.
Причина подтверждается исходниками: composite/filter/shadow не переопределяются.

Рекомендация: для готового full-frame renderer явно задавать source-over, none
для filter и отсутствие теней внутри существующего save/try/finally/restore.
Добавить проверки одинакового результата и восстановления входных настроек,
включая исключение рисования.

Границу с приложением нужно описать отдельно:

- Canvas должен быть пригоден для полного кадра, без заранее ограничивающего clip.
  save/restore не удаляет унаследованный clip; не вводить reset() с побочным
  уничтожением состояния и bitmap ради обхода этого ограничения.
- Renderer работает в bitmap-пикселях и временно игнорирует transform приложения.
  Он не вызывает resize и не управляет devicePixelRatio. Приложение задаёт bitmap
  и CSS-размер; это отличается от примеров собственных логических координат в /scene.
- Исключение Canvas не откатывает уже нарисованные пиксели. Restore восстанавливает
  настройки, а не предыдущую картинку.

Не стоит обещать независимость от любого возможного свойства Canvas. Нужно
перечислить нормализуемые свойства и требования к переданному контексту.

## 3. Перенести проверку progress до изменения картинки

При progress=2 или NaN createSceneFrame отклоняет кадр с RangeError. Но вызов
sceneRenderer.render расположен после рисования фона и заголовка, поэтому
неверный кадр успевает затереть предыдущую картинку. Это воспроизведено и счётчиком
вызовов (два draw до ошибки), и сравнением пикселей на native Canvas.

Рекомендация: проверять конечный progress в диапазоне [0, 1] до любых draw-вызовов
при ненулевом bitmap. Это согласует раннюю проверку с /scene и не требует обещать
откат после произвольной ошибки Canvas. Тесты: -1, 2, NaN и бесконечности; отсутствие
рисования и сохранение контекста/предыдущей картинки. Нулевой bitmap может
сохранить текущий контракт no-op.

Не нужно превращать renderer в полный валидатор произвольных ArraySnapshot.
В частности, positions собирает Map по id: некорректные повторяющиеся id могут
схлопнуться ещё до scene-валидации. Гарантии `/array` относятся к настоящему trace;
для ручных снимков пользователь отвечает за те же инварианты. Динамическая длина,
несколько held и изменение значений не становятся поддерживаемой моделью лишь
потому, что можно вручную собрать объект с типом ArraySnapshot.

## 4. Совместимые уточнения конфигурации

### Опциональный colors

Runtime принимает createArrayRenderer({ theme: 'dark', colors: undefined }) как
обычную тему. При exactOptionalPropertyTypes входной ArrayRendererOptions
отвергает такой объект (диагностика TS2375), хотя отдельные undefined-роли уже
разрешены в ArrayPaletteOverrides.

Рекомендация: colors?: ArrayPaletteOverrides | undefined. Это расширение входного
типа, а не изменение палитры. Проверить оба имени renderer строгим installed-package
consumer. Обязательную theme и текущие названия ролей сохранить.

### Неверная theme в JavaScript

createArrayRenderer({ theme: 'invalid' }) и createArrayRenderer({}) принимаются
без явной ошибки: палитра получается пустой, а цвета рисования — undefined.
TypeScript такие вызовы запрещает, но JS-пользователь получает неясный результат.

Стоит добавить явную проверку light/dark при создании renderer, с TypeError для
отсутствующей или неверной темы. Не вводить молчаливую тему по умолчанию без
отдельной необходимости и не обещать стабильность точного текста ошибки.
Проверять CSS-валидность строк цветов по-прежнему не требуется: документация
явно передаёт эту задачу Canvas. Неподдерживаемые цвета и требования к контексту
не следует смешивать с проверкой конечного набора тем.

## Что сохранить и что отложить

- Сохранить все три runtime-имени и четыре публичных типа. createSortRenderer
  оставить идентичным совместимым псевдонимом; новые примеры пишут createArrayRenderer.
- Не добавлять алгоритмы, управление плеером, экспорт GIF, собственные DOM-контролы
  или регистрацию произвольных объектов в /canvas.
- Строковые роли цветов, копирование входных overrides и создание нового renderer
  для смены темы уже понятны и проверены. Сеттеры палитры не нужны.
- arrayScene оставляет item по ссылке, не делает произвольные данные глубоко
  неизменяемыми и не доказывает корректность ручного снимка.
- Цвета и числовые метаданные берутся из current; held имеет приоритет. Эти правила
  стоит описать в справочнике RU/EN вместе с smoothstep, плотными подписями и DPR.
- Встроенные английские подписи и компоновка остаются частью готового renderer.
  Локализацию, форматирование подписей, configurable easing, подписывание объектов
  и pixel-perfect стабильность не стоит обещать без пользовательского сценария.
- highlight использует includes для каждого столбца: при n столбцах и k выделенных
  id это O(nk). Set один раз на кадр — возможная оптимизация после отдельного замера.
  Создание sceneRenderer внутри каждого render тоже можно оценить отдельно;
  доказанного требования менять публичный API здесь нет.

## Основания проверки

- Прочитаны весь src/canvas/index.ts, сгенерированные декларации, связанные
  ArraySnapshot/ArrayFrame и scene/projector, справочники RU/EN, использование
  в Sorting lab и публичные package fixtures.
- Пройдены 25 тестов из canvas-palette, timeline, bubble-sort, scene,
  scene-projector и public-api, включая 2186 эталонных трасс.
- Отдельные пробы через публичные импорты проверили 0/1/4000/150000 элементов,
  неизменяемость оболочек arrayScene, сохранение ссылки Item, held на позиции
  отверстия, восемь повторных/обратных seek, no-op при нулевом bitmap и restore
  после исключения Canvas. На 150000 воспроизведено описанное падение.
- Native Canvas подтвердил влияние composite/filter/shadow и восстановление
  transform/alpha, а также изменение bitmap до ошибки неверного progress.
- Строгая компиляция отдельного виртуального consumer с exactOptionalPropertyTypes
  подтвердила TS2375 для colors: undefined; runtime-вызов принят.
- Полные 117 тестов, installed-package consumer и CI точного 0bbae18 прошли при
  выпуске 0.11.1. В этом аудите runtime не менялся; будущие исправления требуют
  собственных регрессий и CI нового кандидата. Браузерные FPS не измерялись.

## Рекомендуемый порядок

1. Убрать spread в вычислении максимума, добавить регрессию большого массива.
2. Нормализовать перечисленные настройки рисования и закрепить требования к
   контексту; проверять progress до первого draw-вызова.
3. Разрешить colors: undefined в типах и явно отклонять неверную theme.
4. Дописать контракт /canvas в существующий справочник RU/EN, без разрастания README.
5. Выполнить focused-регрессии, полный набор тестов и installed-package consumer;
   проверить CI точного кандидата перед следующим разрешённым выпуском.

После этих точечных изменений текущий /canvas можно стабилизировать без редизайна.
